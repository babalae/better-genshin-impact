# Pulonia：用户故事与设计边界

[返回总览](README.md) · [路线图](roadmap.md)

这份文档是需求基线。原始故事和社区补充统一编号；来源细节放在[调研依据](research.md)，避免阅读需求时被实现细节打断。

**设计的出发点是让玩家少配置、少空跑、知道实际完成了什么。** 任务树、调度、记录和 API 都服务于这个目标。后续增减实体、页面或依赖时，先说明它解决下列哪条故事；不能仅因技术上可以扩展，就增加一层框架或一种配置方式。

## 用户故事清单

US-01—11 依据本次讨论整理，US-12 来自社区反馈。保留用户目标，不把建议的实现方式当成唯一解法；编号用于后文追踪。2026-10-04 按用户最新要求收缩 US-02 为程序内定时运行，触发不依赖电脑使用状态。

| 编号 | 用户故事 | 用户应当看到的结果 |
| --- | --- | --- |
| US-01 目标驱动托管 | 作为初级玩家，我只想选择要培养的角色和要采集的物品，让程序了解我的角色 box、练度、库存、圣遗物与树脂，按优先级安排培养、每日/每周/每月事项，剩余时间再跑狗粮等可选内容；不想学习脚本仓库和订阅。 | 展示目标缺口、今日安排、资源预算以及选择理由；能一键开始、调整优先级。完整资产识别分阶段实现，识别不到时显示未知并允许补充。 |
| US-02 程序内定时运行 | 作为日常托管用户，我希望在程序运行时，按每日、每周等日程运行指定任务。 | 配置可读的日程和有效时间窗；到点按忙碌策略提交，过期与补触发都有明确记录；程序关闭时不执行，重新启动后按补触发策略处理遗漏。 |
| US-03 刷新与完成判定 | 作为每天采集、刷怪和领奖的玩家，我希望程序记住哪些资源已采、哪些奖励已领，按真实刷新周期跳过，并区分执行失败与已经完成。 | 显示完成依据、剩余 CD、下次可运行时间；中途失败不把整条路线记成功，已完成部分也不丢失；日、周、月限制各自正确。 |
| US-04 自由组合 | 作为喜欢折腾的玩家，我希望将内部功能、路线、JS、宏、Shell 和 C# 组合成新的功能，并复用已有任务组合。 | 在树里分组、排序、重复添加、引用子计划和设置条件；同一能力可以在不同位置使用不同参数，不靠修改脚本拼接流程。 |
| US-05 开发者接入 | 作为开发者，我希望从 C# 调用任务执行接口，也能用 C# 提供新任务，获取状态、结果并取消执行。 | UI、JS、C# 和外部客户端复用同一执行语义；不依赖某个页面先打开；纯 Shell/纯计算任务不会被迫启动截图器。 |
| US-06 中断续跑 | 作为长任务使用者，我希望中断后知道做到哪里，能继续剩余内容，或直接指定从树上的某一项开始。 | 首版做到节点级续跑；保留当时的计划、参数和资源版本；结果不确定的消费/领奖步骤先核验。无需任意脚本逐行恢复。 |
| US-07 异常恢复 | 作为无人值守用户，我希望网络中断、顶号、剧情界面、日切月卡和版本变化等异常不会让程序一直乱点或卡死。 | 已知异常在有限次数与时间内恢复；未知界面或账号风险进入待处理，留下原因和续跑位置。 |
| US-08 快捷触发 | 作为经常使用小功能的玩家，我希望给 JS、任务组合或树中一个子任务设置自己的快捷键。 | 热键能触发任意受支持任务；忙碌、重复按键和取消行为明确，所有入口共同管理输入占用。 |
| US-09 设置清晰一致 | 作为配置者，我希望明确任务实际使用哪套设置、为什么生效；一条龙能直接展示复用的独立任务配置。 | 一条龙页面、树节点和独立运行是不同展示 UI，共用同一套有效参数解析与提交合同，显示有效值与来源；覆盖、继承和共享修改可区分。 |
| US-10 快速找到并添加 | 作为采集玩家，我希望按角色、材料、地区或用途找到任务，快速添加整个目录，不因大量路线而卡住。 | 搜索、预览、批量添加在同一入口完成；支持引用目录和展开编辑，不要求手工复制文件、建链接或运行脚本生成菜单。 |
| US-11 多账号托管 | 作为多账号玩家，我希望自动切换账号，依次执行各账号的一条龙，分别使用对应目标和配置。 | 切换后核验实际 UID；每个账号的目标、预算、进度和 CD 不串用；登录失败不能接着在上一个账号执行。 |
| US-12 编辑成果可保留 | 作为已配好任务的用户，我希望跨计划复制子树时保留完整参数，误删或误拖后能撤销，不必重启程序或手改 JSON。 | 复制参数类型不变、继承差异可见、新节点有新 ID；删除、移动、批量添加可以撤销。来源见[社区需求依据](research.md)。 |

## 用这些故事约束后续设计

1. **默认路径必须短。** 选择角色/物品、确认目标与日程、查看推荐安排、开始运行；共享设置、设置方案、脚本来源和配置继承按需展开。
2. **树编辑器与一条龙页面共用同一计划模型与执行核心，用途只决定界面归属。** 每份一条龙配置是独立的 `PuloniaTaskPlan`，以 `purpose`（General=0 / OneDragon=1）标记在哪个界面出现：普通计划菜单仅列出 General，一条龙配置 ComboBox 仅列出 OneDragon；执行器与底层完整计划目录不区分用途，跨计划引用、校验和资源检查保持可用。任一界面都不另存一份隐式参数，编辑、触发、C# 调用不能再出现多套执行结果。
3. **先完成可替代的任务系统，再逐步扩大识别和规划能力。** 不用“智能规划”掩盖底层没有结果、不能取消、CD 不可信等问题；也不能以只完成执行器为由取消 US-01 的最终托管目标。
4. **公共问题由宿主解决，游戏业务仍由具体能力解决。** 宿主负责配置、时间、身份、记录、输入协调和已知全局中断；材料数据、配队、采集路线和奖励核验留在内容/能力中。社区脚本可以继续提供专业策略。
5. **复杂性要有来源。** 保留 d-v3 的树格式与有用交互，统一使用 `PuloniaTask` 相关命名；不引入 Quartz、SQLite，不增加多机编排、任意并行图或通用规则平台。社区已有外部网站、多人同步方案不自动成为本次交付范围。每条复杂规则都要在下方“复杂规则 → 用户故事”表中登记来源；没有来源的规则要么删除，要么写明“按用户决定保留”。

## 边界分级

边界场景按影响分三级处理，与项目约定“首次实现聚焦主流程，暂不处理的场景用注释记录”一致：

| 级别 | 场景 | 处理方式 |
| --- | --- | --- |
| 必须处理 | 可能在错误账号上执行；重复消耗不可恢复的资源（树脂、购买、领奖）；丢失用户配置或运行状态；游戏输入卡死 | 写完整逻辑 |
| 明确报错即可 | 配置冲突、文件损坏、外部手改文件 | 显示原因，保留现场，不写恢复逻辑 |
| 不处理 | 多处同时编辑同一配置、夏令时、时钟回拨后的去抖、极端数量上限、手改磁盘上的账号图片 | 用一行注释说明 |

当前对应的做法：

- **必须处理**：执行前切号并核验 UID，失败进入待处理；默认账号不主动登出；密码只存在 Windows 凭据管理器；快照不可变，触发请求准入时复核截止时间和配置版本；采集成功与节点结果原子提交；state.json 原子替换、备份回退、损坏时停止自动运行；释放租约时释放全部按键；Shell 结束整个进程树。
- **明确报错即可**：坏的计划文件和历史文件跳过并提示，文件不删除；计划和账号目录的修订冲突直接报错；损坏的 manifest 或路线 JSON 让资源检查显示“有更新”，确认更新时被拒绝；JS 工作目录被另一个运行占用时 10 秒后报错；嵌套获取游戏租约直接报错。
- **不处理**：两个页面共用一个编辑会话，不处理多进程同时编辑；触发器只用三个固定偏移，没有夏令时；热键去抖只用单调计时；账号图片不复核内容。

**配置类数据**（计划、设置方案、账号、偏好、仓库注册、计划顺序）只需要“原子替换 + 后写者胜”。**只有 `state.json`**（队列、活动运行、账本、触发游标）需要单写者和事务语义。
