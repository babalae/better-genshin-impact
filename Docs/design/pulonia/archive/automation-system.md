## 核心决策

1. 使用 `BetterGenshinImpact.Pulonia` 命名空间和 `PuloniaTask` 相关实体；保留 d-v3 的 `root_task / children` 树格式。
2. 一条龙配置与普通计划同为 `PuloniaTaskPlan`，以 `purpose`（General / OneDragon）区分界面归属；一条龙页面沿用旧 OneDragonFlowPage 左右布局，不是任务计划 UI 换皮。当前体力计划设计为绑定已有任务计划，只计算明确选择跟随的字段，不新增、启用或重排任务；自动生成任务计划属于后续能力，详见[体力计划设计](../proposals/resin-plan.md)。所有入口复用同一存储、模型与执行语义，执行器不区分用途。
3. 主链保持“入口 → 任务服务 → 类型执行器”，文件存储旁路提供支持。允许集中构建只读执行树；具体形式在模型阶段结合用户真实配置验收，不再禁止第二种运行时表示，也不照搬层层转发的转换/调度链。
4. 触发、请求有效性与资源 CD 分开；开始执行前固定版本、解析有效配置，运行状态与编辑模型分开。定时与热键仅在程序运行时生效。
5. 游戏会话与截图按需获取，Shell 和纯计算任务不强制启动截图器；首版串行执行，共同管理输入所有权。
6. 完成结果必须附带证据，执行结束不自动等于采集或领奖成功；支持节点级续跑和有限异常恢复。
7. 不引入 Quartz、SQLite、ORM 或通用工作流框架。使用 .NET 调度循环、现有热键和 JSON 文件；当前不要求新增第三方库。

## 开发约定

**每一步完成实现与自查后，提交给用户验收并停止；收到明确通过后才能开始下一步。** 子步骤遵守同样规则。编译成功不能代替用户验收；开始实施以用户指令与开发计划的记录为准。

验收由用户自行选择真实配置、真实资源和实际使用场景进行，不提供或维护验收用 `examples` JSON 或预制成功数据。编译、单元测试、静态检查及代理构造数据通过只属于开发自查，不证明真实数据兼容或业务正确；未得到用户明确结论时保持待验收。具体标准统一见[开发计划的验收规则](development-plan.md#当前状态与验收规则)。

基础任务系统先可用，再补可靠调度、迁移、多账号和目标托管。完整 box、库存与圣遗物识别按能力分步验收，缺失能力明确标记。具体步骤与验收记录只维护在[开发计划](development-plan.md)，其他文档不另存一套进度。
