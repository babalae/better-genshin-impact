## 运行边界

- 定时与热键只在 BetterGI 主实例运行期间生效。程序关闭时不执行，也不由操作系统启动程序；重启后按补触发规则处理遗漏。
- 定时与热键都只生成请求，经 `IPuloniaTaskService` 进入同一串行队列，不直接调用截图器或页面命令。
- 不检测用户活动，不区分用户输入与模拟输入。
- 手动命令行 `--pulonia-run <planId>` 是用户显式提交，程序已启动时经单实例 IPC 交给主实例，不经旧任务页、不提前启动截图器。它不是自动日程的启动机制。

## 触发器模型

触发器 `PuloniaTaskTrigger` 嵌入计划的 `triggers`：

| 字段 | 说明 | 默认值 |
| --- | --- | --- |
| `id` | `trg_` 加 16 位 | 新建生成 |
| `kind` | `Schedule`（定时）或 `Hotkey`（热键） | `Schedule` |
| `enabled` | 是否启用；新建的触发器先以禁用状态保存 | `false` |
| `activated_at_utc` | 配置生效时间，启用或修改时刷新；既是配置版本，也是补触发的下限 | 保存时间 |
| `cron` | 五段数字 Cron | `0 4 * * *` |
| `server_time_zone` | 解释 Cron 的固定偏移：`UtcPlus8`（+8）、`Europe`（+1）、`America`（-5） | `UtcPlus8` |
| `window_minutes` | 允许延迟启动的分钟数，1—10080；也作为请求的截止时间 | 360 |
| `catch_up` | 离线或睡眠后是否补最近一次 | `true` |
| `busy_policy` | `Skip`、`QueueOnce`、`StopCurrent` | `Skip` |
| `hotkey`、`hotkey_type` | 热键键位与模式（`GlobalRegister` 或 `KeyboardMonitor`） | 模型默认 `Ctrl + Alt + F8` 全局注册；界面“新增快捷键触发”默认键鼠监听 `F8` |
| `target_task_id` | 只运行计划中的某个子树；缺省运行整个计划 | 空 |
| `account_id` | 普通计划的账号参数资料（不切号）；一条龙忽略此字段，使用配置绑定的运行账号 | 空 |

时区只有上述三个固定偏移，不使用 `TimeZoneInfo`，也没有夏令时规则。触发器时区与路线 CD 使用的服务器时区（`PuloniaServerTime`）相互独立。`catch_up` 与 `window_minutes` 合并、界面以时间表单为主而把 Cron 收进高级，待定 D9。

## Cron

- 五段：分、时、日、月、星期；支持数字、`*`、列表 `,`、范围 `-` 和步长 `/`；星期 0 与 7 都是周日。
- 日与星期同时限制时取交集。不支持秒段、名称和 Quartz 的 `? L W #`；没有该日期的月份跳过。
- 保存时要求从生效时间起 8 年内至少有一次有效时间。
- 编辑器提供“快捷设置”：预设（每 5 分钟、每 15 分钟、每小时、每天 04:00、工作日 09:00、每周一 04:00、每月 1 日 04:00）点击即写入；“周期执行”“固定时间执行”组合后点“应用到表达式”。
- d-v3 的 Quartz 表达式导入时，能等价表示的转换成五段 Cron，不能表示的保留原文并标为待调整，不静默改变时间语义。

## 定时检查

`PuloniaTaskTriggerHost` 每秒调用一次 `IPuloniaTaskService.CheckTriggersAsync`。同一时刻只有一个检查或热键在处理（触发门），它也是触发游标的唯一写入路径。

每个启用的定时触发器：

1. 取游标的 `last_occurrence_utc`；游标不存在或 `trigger_activated_at_utc` 与当前配置不同时，从生效时间重新开始。
2. 在“上次处理时刻”与“现在减允许延迟时间”两者较晚者之后，找最近一次到点时间。
3. 没有可启动的时刻但已经错过：游标推进到现在，记为“遗漏”（超过允许延迟启动时间）。
4. `catch_up = false` 且本次到点算作遗漏时：游标推进到该时刻，记为“遗漏”。判定规则：
   - 检查时刻晚于到点时间不超过 5 秒，按准点处理（首轮检查只用这一容差）；
   - 两轮检查间隔不超过 30 秒视为持续轮询，上一轮之后才到点的时刻按在线到点处理，即使本轮因忙碌晚到；
   - 间隔超过 30 秒（系统睡眠或调度停顿）时，期间到点的时刻按离线遗漏处理。
5. 其余情况按忙碌策略提交请求。

一次恢复只合并仍可延迟启动的最近一次，不补跑整段离线历史。请求的截止时间为到点时刻加 `window_minutes`。

### 游标

state.json 的 `trigger_states` 只保存防重复所需的四个字段：`plan_id`、`trigger_id`、`trigger_activated_at_utc`、`last_occurrence_utc`。入队请求与游标前移在同一次 state.json 替换中提交；`Latest` 只返回严格晚于游标的时刻，因此重启和时钟回拨都不会重放同一时刻。

- 每轮剔除已删除计划或触发器（含旧版写下的热键游标）的孤儿游标，只在确有孤儿时写盘。
- 停用的定时触发器保留游标，撤销编辑恢复旧配置版本时仍能防止重放。
- 读取失败的计划，其游标和运行反馈保留不动，修复后不会重放已处理的时刻。

最近一次处理结果 `PuloniaTaskTriggerStatus`（`Outcome` 为 Waiting、Submitted、Missed、Merged、PrepareFailed，以及消息、关联运行和下次时间）只在内存维护，由 `GetTriggerStatuses` 提供给界面，不写入 state.json。

### 计划重载

- 本进程保存或删除计划后，下一轮检查（约 1 秒后）重新读取全部计划。
- 另每 30 秒比较一次计划文件修改标记（`PuloniaTaskStore.GetPlanFilesStamp`），变化才重读；上次有计划读取失败时也按此周期重试。
- 读取使用 `ListPlansWithFailuresAsync`：一份坏计划只跳过它自己，其余计划照常调度，状态栏提示跳过的文件。

## 忙碌策略与准入

“忙碌”指同一计划、同一账号已有未结束的请求。

| 策略 | 忙碌时 |
| --- | --- |
| `Skip` | 不提交，游标前移，记为“已合并” |
| `QueueOnce` | 已有排队请求时同 `Skip`；只有运行中的请求时再排一个 |
| `StopCurrent` | 已有排队请求时同 `Skip`；否则入队，写盘成功后调用 `TaskStopService.StopAll`，并让该请求在队列中优先 |

不同计划同时到期默认依次排队。提交时不做二次忙碌复核，手动或续跑请求与触发提交之间存在窄竞态，最坏多排一个请求。`StopCurrent` 会停止所有已注册的本地运行，而不只是同一计划，与界面文案“同一计划 / 账号已忙碌时”不完全一致；限定范围或删除该策略待定 D8。启用 `StopCurrent` 的触发器需要二次确认。

触发器请求出队时复核：触发器仍存在、已启用、配置版本未变，一条龙的账号绑定未变，否则记为“已取消”；超过截止时间记为“已过期”；都不执行任务。

## 热键

热键复用 `HotKeySettingModel`，两种模式：

- **全局注册**（`GlobalRegister`）：组合键或功能键；不接受鼠标键和 F12，无修饰键时只允许 F1—F24。
- **键鼠监听**（`KeyboardMonitor`）：无修饰的单键或鼠标侧键（XButton1/XButton2），随现有键鼠监听的启停、游戏前台与聊天屏蔽规则生效，不另装钩子。

键位规则在 `PuloniaTaskHotkeyValidator` 中，只在保存触发器前和注册热键前检查；计划加载不检查键位，保存过的非法键位只会在注册时报错，不影响计划读取。

- **冲突**：软件已有快捷键优先。注册前用反射读取 `HotKeyConfig` 预检冲突（命令行 `--pulonia-run` 启动时，计划热键可能先于应用热键注册，按先到先得会让应用热键失败，因此保留预检）。键鼠监听不区分修饰键，监听 `F8` 与全局 `Ctrl+F8` 视为冲突。注册失败显示原因，每 30 秒随计划检查重试，不注销原功能。
- **去抖**：同一热键 1 秒内重复按下只算一次，在内存中用单调计时（`Environment.TickCount64`）判断，不写 state.json，时钟回拨不会吞掉热键。
- **提交**：与定时使用相同的忙碌策略与准入，不写游标。
- **释放**：主实例关闭时在所属 UI 线程的 `ShutdownStarted` 中统一释放两种模式的注册。

## 连续运行批次（步骤 10.2，已确认范围，未实现）

“更多 → 连续运行”勾选已有一条龙计划并排序，支持同账号多配置和多账号各自配置；可立即运行，也可保存具名批次并配置定时或热键。成员保留独立快照、实际 UID 和历史，以同一 `BatchId` 关联，连续串行运行；切号失败的成员进入待处理，释放输入后继续下一项，整批停止时取消未开始的成员。提交时统一校验全部成员快照，不部分入队；中断的批次不自动继续。

任一已保存批次有启用的定时触发器时，其成员的独立定时全部不提交运行：原开关和日程保留，界面显示“已由批次定时接管”。多个批次按集合合并接管；全部禁用或删除批次定时、删除批次或移除成员后，没有其他接管者才恢复，且不补跑被接管期间的时刻。仅热键或已禁用的定时不接管；手动、热键和续跑不受影响。每轮调度先用一致的配置计算接管关系，再计算到期；已排队的独立定时在准入时复核，运行中的请求不强停。
