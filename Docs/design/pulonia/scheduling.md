## 运行边界

- 每个实例（主实例、桌面分身、云原神实例）都运行 `PuloniaTaskTriggerHost`，只检查本实例负责的定时触发器：执行实例包含本实例的触发器；`instances` 为空的只由主实例处理。定时只在执行实例运行期间生效。程序关闭时不执行，也不由操作系统启动程序；实例重启后按自己的游标和补触发规则处理遗漏。
- 计划热键只在主实例注册，按下后只在主实例执行。子实例不注册计划热键，不支持热键触发，见[热键](#热键)和[下一节](#多个实例同时存在时不会重复触发)。
- 定时与热键都只生成请求，在本实例经 `IPuloniaTaskService` 提交，进入本实例的队列，不经过 IPC，也不直接调用截图器或页面命令。一步下发（`pulonia.run.submit`）只用于主实例界面上的手动“运行于”，见[执行 · 跨实例执行](execution.md#跨实例执行一步下发)。
- 不检测用户活动，不区分用户输入与模拟输入。
- 手动命令行 `--pulonia-run <planId>` 是用户显式提交，在启动参数所在的实例本地提交，进入该实例的队列，不转到其他实例执行。主实例已启动时，参数经单实例 IPC 交给运行中的主实例。不经旧任务页、不提前启动截图器。它不是自动日程的启动机制。

## 多个实例同时存在时不会重复触发

触发器嵌在共享的计划文件里，所有实例都能读到，但每个定时触发器只由它的执行实例检查（[统筹设计 6.4.1](../instance-account-model.md#641-多个实例同时存在时会不会重复触发)）：

- 每个实例的 `PuloniaTaskTriggerHost` 每秒检查一次定时，只处理执行实例包含本实例的触发器；`instances` 为空的触发器只由主实例处理。
- 一个（触发器，执行实例）组合只有一个检查者，就是该执行实例自己。同一 Windows 用户下，一个实例键不会同时有两个进程：主实例只有一个，桌面分身同时只有一个，同名云原神实例由实例名互斥体保证只运行一个。
- 触发游标存在执行实例自己的 state.json 里，入队与游标前移在同一次替换中提交。实例重启后按游标继续，不会重放已处理的时刻。
- 计划热键只在主实例注册、只在主实例执行（[统筹设计 6.4.3](../instance-account-model.md#643-计划热键)），不会在多个实例上响应。

同一时刻有多个定时触发器到点时：

| 情况 | 结果 |
| --- | --- |
| 执行实例不同 | 各实例各自提交，并行运行 |
| 执行实例相同 | 依次进入该实例的队列，串行运行，忙碌时按各触发器的忙碌策略处理 |
| 一个触发器选了多个执行实例 | 每个执行实例各自检查、各自提交一次，并行运行 |

执行实例没有运行时，没有进程检查它的定时。主实例不替它检查，也不启动离线的实例（统筹设计 A10；原待定 A3 不再需要）。实例启动后按自己的游标和补触发规则处理遗漏，见[定时检查](#定时检查)。

## 触发器模型

触发器 `PuloniaTaskTrigger` 嵌入计划的 `triggers`：

| 字段 | 说明 | 默认值 |
| --- | --- | --- |
| `id` | `trg_` 加 16 位 | 新建生成 |
| `kind` | `Schedule`（定时）或 `Hotkey`（热键） | `Schedule` |
| `enabled` | 是否启用；新建的触发器先以禁用状态保存 | `false` |
| `activated_at_utc` | 配置生效时间，启用或修改时刷新；既是配置版本，也是补触发的下限 | 保存时间 |
| `cron` | 五段数字 Cron | `0 4 * * *` |
| `server_time_zone` | 解释 Cron 的固定偏移：`UtcPlus8`（+8）、`Europe`（+1）、`America`（-5）；只用于解释 Cron | 新建时计划指定了账户取该账户的服务器时区，否则 `UtcPlus8` |
| `window_minutes` | 允许延迟启动的分钟数，1—10080；也作为请求的截止时间 | 360 |
| `catch_up` | 离线或睡眠后是否补最近一次 | `true` |
| `busy_policy` | `Skip`、`QueueOnce`、`StopCurrent` | `Skip` |
| `hotkey`、`hotkey_type` | 热键键位与模式（`GlobalRegister` 或 `KeyboardMonitor`） | 模型默认 `Ctrl + Alt + F8` 全局注册；界面“新增快捷键触发”默认键鼠监听 `F8` |
| `target_task_id` | 只运行计划中的某个子树；缺省运行整个计划 | 空 |
| `instances` | 执行实例键的列表：`primary`、`child_session`、`webview:<小写实例名>`；为空表示只在主实例执行。只对定时触发器有效，热键触发器必须为空 | 空 |

删除原 `account_id`（普通计划的账号参数资料）。触发器不能覆盖计划的运行账户设置，运行账户在运行开始时由计划设置和执行实例的当前账户决定，见[执行 · 队列与执行顺序](execution.md#队列与执行顺序)。

执行实例 `instances` 的规则（[统筹设计 6.4.2](../instance-account-model.md#642-定时触发)）：

- 只对定时触发器有效。热键触发器没有执行实例选项，保存时要求 `instances` 为空（[统筹设计 6.4.3](../instance-account-model.md#643-计划热键)）。
- 可选主实例、桌面分身和已建立的各云原神实例。界面列出全部实例，不要求在线。
- 计划指定了账户时只能选一个执行实例，因为同一账户不能同时运行。
- 选了多个执行实例时，保存前按[账户占用](../instance-account-model.md#45-账户占用)检查这些实例的当前账户是否重复。
- 计划指定了账户、执行实例是云原神，且该实例的当前账户不是这个账户时，保存前提示：“云原神实例不能切换账户，到点时需要该实例登录着乙。”
- 带 `account_id` 的旧格式触发器不转换：计划格式版本不是 4 时拒绝读取，旧计划需删除后重建，见[统筹设计第 11 节](../instance-account-model.md#11-迁移)。

时区只有上述三个固定偏移，不使用 `TimeZoneInfo`，也没有夏令时规则。触发器的 `server_time_zone` 只用于解释 Cron，与账户的服务器时区相互独立；路线 CD 的日切按运行账户的 `server_time_zone` 计算，见[结果、CD 与存储](results-and-storage.md)。`catch_up` 与 `window_minutes` 合并、界面以时间表单为主而把 Cron 收进高级，待定 D9。

## Cron

- 五段：分、时、日、月、星期；支持数字、`*`、列表 `,`、范围 `-` 和步长 `/`；星期 0 与 7 都是周日。
- 日与星期同时限制时取交集。不支持秒段、名称和 Quartz 的 `? L W #`；没有该日期的月份跳过。
- 保存时要求从生效时间起 8 年内至少有一次有效时间。
- 编辑器提供“快捷设置”：预设（每 5 分钟、每 15 分钟、每小时、每天 04:00、工作日 09:00、每周一 04:00、每月 1 日 04:00）点击即写入；“周期执行”“固定时间执行”组合后点“应用到表达式”。
- d-v3 的 Quartz 表达式导入时，能等价表示的转换成五段 Cron，不能表示的保留原文并标为待调整，不静默改变时间语义。

## 定时检查

每个实例的 `PuloniaTaskTriggerHost` 每秒调用一次本实例的 `IPuloniaTaskService.CheckTriggersAsync`。同一实例内同一时刻只有一个检查或热键在处理（触发门），它也是本实例触发游标的唯一写入路径。

本实例只处理执行实例包含本实例的启用定时触发器；`instances` 为空的只由主实例处理。每个这样的触发器：

1. 取本实例中该触发器游标的 `last_occurrence_utc`；游标不存在或 `trigger_activated_at_utc` 与当前配置不同时，从生效时间重新开始。
2. 在“上次处理时刻”与“现在减允许延迟时间”两者较晚者之后，找最近一次到点时间。
3. 没有可启动的时刻但已经错过：游标推进到现在，记为“遗漏”（超过允许延迟启动时间）。
4. `catch_up = false` 且本次到点算作遗漏时：游标推进到该时刻，记为“遗漏”。判定规则：
   - 检查时刻晚于到点时间不超过 5 秒，按准点处理（首轮检查只用这一容差）；
   - 两轮检查间隔不超过 30 秒视为持续轮询，上一轮之后才到点的时刻按在线到点处理，即使本轮因忙碌晚到；
   - 间隔超过 30 秒（系统睡眠或调度停顿）时，期间到点的时刻按离线遗漏处理。
5. 其余情况按忙碌策略在本实例本地提交请求，进入本实例的队列，不经过 IPC。

一次恢复只合并仍可延迟启动的最近一次，不补跑整段离线历史。请求的截止时间为到点时刻加 `window_minutes`。

执行实例没有运行时，没有进程检查它的定时。实例启动后按自己的游标和补触发规则（`catch_up`、`window_minutes`）处理遗漏：仍在允许延迟时间内的最近一次补跑，超过的记为遗漏。不改到其他实例执行，主实例也不替它启动实例。执行实例已被删除（例如删掉了云原神实例）时，没有实例检查这个组合，触发设置页提示“执行实例不存在”。

### 游标

游标存在执行实例自己的 state.json（`User/Pulonia/instances/<目录名>/state.json`）中，按（计划、触发器）记录。`trigger_states` 只保存防重复所需的字段：`plan_id`、`trigger_id`、`trigger_activated_at_utc`、`last_occurrence_utc`。一个触发器选了 A、B、C 时，三个实例各有一份游标，各自前移，互不影响。

入队请求与游标前移在本实例的同一次 state.json 替换中提交。`Latest` 只返回严格晚于游标的时刻，因此重启和时钟回拨都不会重放同一时刻。

- 每轮剔除孤儿游标，只在确有孤儿时写盘。孤儿包括：计划或触发器已删除（含旧版写下的热键游标），以及触发器的执行实例已不再包含本实例。执行实例改回包含本实例时，游标从生效时间重新开始。
- 停用的定时触发器保留游标，撤销编辑恢复旧配置版本时仍能防止重放。
- 读取失败的计划，其游标和运行反馈保留不动，修复后不会重放已处理的时刻。
- 根目录旧 `User/Pulonia/state.json` 中的游标不转换，旧文件需删除，见[统筹设计第 11 节](../instance-account-model.md#11-迁移)。删除后没有游标的触发器按[定时检查](#定时检查)第 1 步从生效时间重新开始。

最近一次处理结果 `PuloniaTaskTriggerStatus`（`Outcome` 为 Waiting、Submitted、Missed、Merged、PrepareFailed，以及消息、关联运行和下次时间）只在执行实例的内存中维护，由本实例的 `GetTriggerStatuses` 提供给界面，不写入 state.json。触发设置页实时显示本实例负责的部分；其他实例负责的部分，每 10 秒读取一次它们 state.json 中的游标和 `online.lock`，只显示游标记录的上次处理时刻和是否在线，例如“云原神 · 小号A：在线，已处理到 04:30；云原神 · 小号B：未运行”。游标在提交、合并和遗漏时都会前移，所以从其他实例看不出那一次是否真的提交了运行，要看执行记录。

### 计划重载

- 本进程保存或删除计划后，下一轮检查（约 1 秒后）重新读取全部计划。
- 另每 30 秒比较一次计划文件修改标记（`PuloniaTaskStore.GetPlanFilesStamp`），变化才重读；上次有计划读取失败时也按此周期重试。在另一个实例修改触发器，最多 30 秒后生效。
- 读取使用 `ListPlansWithFailuresAsync`：一份坏计划只跳过它自己，其余计划照常调度，状态栏提示跳过的文件。

## 忙碌策略与准入

“忙碌”指本实例里同一计划已有未结束的请求。忙碌策略在本实例的队列上判断：定时在执行实例判断，热键在主实例判断。

| 策略 | 忙碌时 |
| --- | --- |
| `Skip` | 不提交，游标前移，记为“已合并” |
| `QueueOnce` | 已有排队请求时同 `Skip`；只有运行中的请求时再排一个 |
| `StopCurrent` | 已有排队请求时同 `Skip`；否则入队，写盘成功后调用本实例的 `TaskStopService.StopAll`，并让该请求在本实例的队列中优先 |

同一执行实例上不同计划同时到期时依次排队；执行实例不同时各自提交，并行运行。提交时不做二次忙碌复核，手动或续跑请求与触发提交之间存在窄竞态，最坏多排一个请求。`StopCurrent` 会停止执行实例中所有已注册的运行，而不只是同一计划，其他实例不受影响；这与界面文案“同一计划 / 账号已忙碌时”不完全一致，限定范围或删除该策略待定 D8。启用 `StopCurrent` 的触发器需要二次确认。

触发器请求在执行实例出队时复核：触发器仍存在、已启用、配置版本未变，计划的运行账户设置未变，否则记为“已取消”；超过截止时间记为“已过期”；都不执行任务。

## 热键

热键复用 `HotKeySettingModel`，两种模式：

- **全局注册**（`GlobalRegister`）：组合键或功能键；不接受鼠标键和 F12，无修饰键时只允许 F1—F24。
- **键鼠监听**（`KeyboardMonitor`）：无修饰的单键或鼠标侧键（XButton1/XButton2），随现有键鼠监听的启停、游戏前台与聊天屏蔽规则生效，不另装钩子。

键位规则在 `PuloniaTaskHotkeyValidator` 中，只在保存触发器前和注册热键前检查；计划加载不检查键位，保存过的非法键位只会在注册时报错，不影响计划读取。

- **冲突**：软件已有快捷键优先。注册前用反射读取 `HotKeyConfig` 预检冲突（命令行 `--pulonia-run` 启动时，计划热键可能先于应用热键注册，按先到先得会让应用热键失败，因此保留预检）。键鼠监听不区分修饰键，监听 `F8` 与全局 `Ctrl+F8` 视为冲突。注册失败显示原因，每 30 秒随计划检查重试，不注销原功能。
- **去抖**：同一热键 1 秒内重复按下只算一次，在内存中用单调计时（`Environment.TickCount64`）判断，不写 state.json，时钟回拨不会吞掉热键。
- **提交**：计划热键只在主实例注册，按下后在主实例本地提交，进入主实例的队列。热键触发器没有执行实例选项，保存时要求 `instances` 为空。与定时使用相同的忙碌策略与准入，不写游标。
- **子实例**：不注册计划热键，不支持热键触发。云原神实例与主实例在同一个 Windows 会话里，同一组合键只能被一个进程全局注册，键鼠监听又会在每个进程里重复响应；桌面分身只在焦点位于主实例的分身窗口时才收到键盘输入。需要在子实例运行计划时，用子实例自己的界面、定时触发器，或主实例的“运行于”。
- **释放**：主实例关闭时在所属 UI 线程的 `ShutdownStarted` 中统一释放两种模式的注册。

## 连续运行批次（步骤 10.2，已确认范围，未实现）

“更多 → 连续运行”勾选已有一条龙计划并排序，支持同一账户多份配置和多账户各自配置；可立即运行，也可保存具名批次并配置定时或热键。成员保留独立快照、运行账户和历史，以同一 `BatchId` 关联，连续串行运行；切换账户失败的成员进入待处理，释放输入后继续下一项，整批停止时取消未开始的成员。提交时统一校验全部成员快照，不部分入队；中断的批次不自动继续。

任一已保存批次有启用的定时触发器时，其成员的独立定时全部不提交运行：原开关和日程保留，界面显示“已由批次定时接管”。多个批次按集合合并接管；全部禁用或删除批次定时、删除批次或移除成员后，没有其他接管者才恢复，且不补跑被接管期间的时刻。仅热键或已禁用的定时不接管；手动、热键和续跑不受影响。每轮调度先用一致的配置计算接管关系，再计算到期；已排队的独立定时在准入时复核，运行中的请求不强停。
