## 三个问题分别回答

| 问题 | 由谁处理 | 示例 |
| --- | --- | --- |
| 什么时候发起？ | 触发器 `PuloniaTaskTrigger` | 每天 04:00 |
| 现在能不能开始？ | 请求准入与节点开关 | 触发器仍启用、未超过截止时间、节点已启用 |
| 这个资源现在能不能再做？ | 路线 CD 与完成记录 | 这份路线文件距运行账户上次完成还没到刷新时间 |

“每周跑一次”是执行偏好，“某奖励每周只能领一次”是游戏事实，两者分开处理。

## 完成合同

执行器返回 `PuloniaTaskOutcome`，完成程度 `Kind` 为 Succeeded、ExecutedUnverified、PartiallySucceeded、Failed、Cancelled、Skipped、NeedsAttention，另带消息、结构化数据、证据和机器可读原因码 `ReasonCode`（如“树脂不足，未执行挑战”）。Succeeded 与 ExecutedUnverified 都让节点记为成功，但只有 Succeeded 能写入完成记录、产生路线 CD，续跑时也只有 Succeeded 的节点视为已完成。

| 场景 | 可以确认什么 | 处理 |
| --- | --- | --- |
| Shell 退出码为 0 | 进程按约定成功 | 节点成功，不推出任何游戏资源完成 |
| 地图追踪整份文件执行成功 | 路线执行完毕 | 按文件估算采集完成，写入运行账户的完成记录 |
| 地图追踪中途放弃、重试耗尽、取消、超时 | 文件未完整执行 | 不写完成记录，下次可整份重跑 |
| 旧 JS、键鼠录制正常返回 | 脚本执行结束 | 默认“已执行、未核验”，不写完成记录 |
| 独立任务返回结构化结果 | 按任务各自的结果合同 | 首领讨伐的累计领奖次数由编排层按运行账户单独记录，见[配置类数据](#配置类数据) |

通用的完成事件报告、额度规则、执行前操作意图和未决操作已于 2026-10-24 删除：唯一的声明方是示例任务，生产能力从未使用。其他能力需要次数或周期限制时，按各自的完成证据单独实现，不预设统一框架。设计这类规则时仍要区分滚动 CD、按服务器日历的周期额度和开放日；时间统一存 UTC，周期边界按服务器时区计算。

### 防止重复执行与崩溃后的误判

1. 路线 CD 在执行前判定，不预先写入占用。整份文件成功后按固定顺序写入，两步都落盘后才继续：
   1. 先写完成记录：在 `.writer.lock` 内读改写运行账户的 `route-completions.json`，耐久替换。
   2. 再写节点结果和本次完成的路线：写入本实例的 `state.json`。
2. 同一运行、同一节点、同一次尝试重复写入完成记录时幂等，按 `run_id`、`task_address`、`attempt` 判断。
3. 崩溃发生在完成记录写入前，按未成功处理，可重跑整份文件。完成记录写入后、节点结果写入前崩溃时，完成记录已经存在，运行在重启后转为“已中断”；续跑或下次运行时，这份路线按 CD 跳过，不会重复执行。
4. 程序崩溃后，遗留的活动运行在启动时转为“已中断”，不当作从未执行；关键状态写盘失败时（包括完成记录写入失败）熔断，停止本实例的自动运行并让运行进入待处理，不把采集成功当作普通失败自动重试。

完成记录在账户目录，节点结果在实例运行状态，两者不能在一次文件替换里提交，所以顺序固定为先完成记录、后节点结果。游戏操作与本地文件同样无法同时提交，因此不承诺任意任务严格只执行一次，只通过“成功后立即落盘”和中断态缩小重复窗口。遇到 CD 默认跳过当前节点并继续后续任务，不原地等待。

## 文件级路线 CD

当前唯一的执行前资源限制（US-03），界面称“路线 CD”（2026-10-28 前称“采集 CD”），代码称 route cooldown。路线 CD 不单独存储，由两部分推算：刷新规则属于计划设置，运行时固定进快照；完成记录属于运行账户的进度。适用于 Pulonia 地图追踪节点，包括目录展开、计划引用、定时、手动和续跑入口；旧配置组和 JS 内部的路线调用不接入。2026-10-28 按[路线 CD 提案](proposals/cooldown-visibility.md)改造，规则表、模式、状态与原因码按改造后的代码核对。

### 成功的定义

以一份地图追踪 JSON 为最小单位：全部路径段完整执行成功，才以文件结束时间估算“该文件的采集已完成”。不核验实际拾取，也不保存文件内的部分成功。

`Pathing()` 返回每次调用独立的不可变对象 `PathingResult`：

| 字段 | 内容 |
| --- | --- |
| `IsSuccess` | 整份文件成功执行为 true；任一路径段提前退出或重试耗尽为 false |
| `SuccessFightCount` | 本次执行已确认的成功战斗次数，不是击杀数；每次重新统计 |
| `ErrorMessage` | 空路线、准备失败、提前结束或重试耗尽等已知原因；成功时为空 |
| `ReviveCount` | 预留，当前为 null；只有已统计且无复活时才为 0 |
| `CollectedItems` | 预留的拾取明细，当前为 null；已统计但无拾取时才是空集合 |

未统计的字段显示为“未统计”，不冒充 0。结果对象随节点结果序列化进运行记录；宿主只根据明确成功的完成状态写入完成记录。旧历史中的 `success_end`、`fully_executed` 只保留展示，不参与判定。

### 身份与规则

- **路线身份**：仓库路线为 `repository:<仓库 ID>/<小写相对路径>`；本地路线为 `local:<小写规范化绝对路径>`。身份不含计划、节点、版本或内容哈希。
- 同一账户的同一路线跨计划、跨实例共享 CD，内容更新后保留 CD；移动、重命名或复制到新位置视为新路线。不同路线的点位重叠不去重。
- **材料规则**：从文件所在目录向上，精确匹配最近的材料名、别名或类别目录名，最近一级命中即停止。规则表集中在 `PuloniaRouteRefreshRuleCatalog`（来源为[采集物刷新文档](../../technical/genshin-collectable-respawn.md)，不在运行时解析 Markdown）：

| 类别 | 规则 |
| --- | --- |
| 特产（含石珀、夜泊石、清水玉）及明确的植物、食材、生物 | 滚动 12、24 或 46 小时，按文档分档 |
| 钓鱼（含官方仓库目录 `提瓦特钓鱼指南`） | 滚动 72 小时 |
| 晶核、晶蝶（参考规则）；魔物、怪物、普通怪、普通怪物、精英怪、精英怪物、地方传奇、地脉花、盗宝团 | 下一次服务器 04:00 |
| 类别目录 `敌人与魔物`、`锄地专区` | 下一次服务器 04:00；位于材料目录之上，材料规则优先 |
| 矿石（含官方仓库目录 `魔晶矿`） | 成功当天的服务器日期加 1、2 或 3 天的 00:00，显示“午夜保守估算” |
| 宝箱、岩之印调查 | 一次性，成功后不再自动执行 |
| 圣遗物、木材（含 `木材伐木点`）、摩拉盒等混合类别 | 识别为“混合类别”，不检查 CD |
| 未匹配任何目录 | “未识别”，不检查 CD，界面单独提示 |

不确定的数据在规则说明中标为参考规则。不实现木材循环刷新，也不实现调查、击杀（每日 400 只）、领奖的全局额度。按官方脚本仓库提交 `d775a4b` 的 5315 个路线文件统计，自动识别覆盖 3875 个（73%）；未识别的 1440 个中 1386 个在 `食材与炼金`，需先补刷新数据。统计方法见[提案 1.1 节](proposals/cooldown-visibility.md#11-魔物路线几乎没有-cd)，单元测试用一组真实目录样本防止规则表回退。

### 设置

刷新规则是计划的共享设置：`pathing` 参数 `route_cd` 是一个对象，按[有效参数解析规则](model.md#有效参数解析规则)整体参与各层覆盖，不深合并。缺省为 `{ "mode": "auto" }`。

| `mode` | 字段 | 含义 |
| --- | --- | --- |
| `auto` | — | 按目录匹配上表；忽略 `reset_hour`、`reset_weekday`，每日边界为 `PuloniaServerTime.DayResetHour`（4 点） |
| `disabled` | — | 不检查 CD |
| `rolling` | `hours` | 成功时刻加固定小时数 |
| `daily` | `reset_hour`（0—23，默认 4） | 下一个服务器游戏日开始时 |
| `calendar_days` | `days` | 服务器时区当天日期加若干天的 00:00 |
| `weekly` | `reset_hour`、`reset_weekday`（1 为周一，7 为周日，默认周一 4 点） | 下一个游戏日后顺延到指定星期 |
| `once` | — | 有成功记录后不再执行 |

代码中模式为枚举 `PuloniaRouteRefreshMode`，参数和快照仍写上表的字符串。规则对象 `PuloniaRouteRefreshRule` 的来源为枚举 `PuloniaRouteRefreshRuleSource`（Directory、Mixed、Unmatched、Manual），快照字段 `refresh_rule` 中写中文取值（“目录自动识别”“混合类别”“未匹配规则”“手动覆盖”）。规则说明文字只由 `PuloniaRouteRefreshRule.Description` 生成。Schema 只有 `PuloniaRouteCooldown.CreateSchema` 一份，执行器和设置目录都引用它。

表单只给三种选择：按材料自动识别（推荐）、不检查 CD、自定义周期；选择自定义后再选“每隔 N 小时”“每日”“每周”“日期间隔”“只执行一次”，存储格式不变。共享设置行显示规则摘要（“自动识别”“每日 04:00”“不检查”等）。

日与周边界使用 `PuloniaServerTime.GetGameDate`（按服务器偏移减去日切小时取日期）。服务器偏移取运行账户的 `server_time_zone`（`UtcPlus8`、`Europe`、`America`），在运行开始确定运行账户时写入运行记录的 `ServerUtcOffsetMinutes`，续跑沿用原运行的偏移；不再在入队时按通用配置填写。界面上的判定取[完成记录](#完成记录)中选出的账户的服务器时区。

准备快照固定本节点的刷新规则，排队期间修改设置不影响本次运行。修改规则或关闭限制后，下一次判定从原完成时间按新规则重新计算，不改写完成记录；不检查及未识别时，完整成功仍写入完成记录。

### 状态与判定

唯一的判定函数是 `PuloniaRouteCooldown.GetStatus(rule, latestCompletion, now, serverOffset)`，运行判定、运行预览、任务树标记、路线 CD 总览和 CD 表单都调用它。运行时只读运行账户的完成记录；地图追踪节点需要游戏，所以含地图追踪节点的运行一定有运行账户。

| 状态 `PuloniaRouteCooldownState` | 条件 | 本次运行 |
| --- | --- | --- |
| Ready（可执行） | 没有完成记录，或已到下次可执行时间 | 执行 |
| CoolingDown（CD 中） | 有记录，未到按当前规则重算的下次可执行时间 | 跳过，原因码 `pathing.cooldown_active` |
| Completed（已完成） | 一次性规则且有记录 | 跳过，原因码 `pathing.cooldown_completed` |
| Unmatched（未识别） | 自动识别没有命中 | 执行 |
| NotChecked（不检查） | 用户关闭或混合类别 | 执行 |

跳过的节点结果为 Skipped，带上述原因码与 `route_*` 数据，消息形如“已跳过：仍在 CD，10-30 04:00 后可执行（落落莓 · 成功后 46 小时）”；同时更新运行的当前节点与消息（只在内存）。运行汇总按原因码把“路线 CD 跳过 N”与其他跳过分开。界面时间一律按本机时间显示；结果数据中的时间仍存 UTC ISO 字符串。成功后的下次可执行时间只计算一次，写入节点结果；完成记录不保存它，判定时按当前规则重新计算。

### 按账户存放

完成记录直接按账户存放在 `accounts/<账户 ID>/route-completions.json`，不再有作用域键，也没有资源键、事件键和周期键。

- 写入和运行判定都使用运行账户：跟随当前账户的运行为实例当前账户，指定账户的运行为计划指定的账户。运行账户在运行开始时确定，规则见[多账户](accounts.md)。
- 同一账户的完成记录被所有计划、所有实例共用：同一账户今天在主实例跑、明天在云原神跑，用的是同一份记录。不同账户的记录互不影响。
- 记录内用[路线身份](#身份与规则)区分路线，身份规则不变。

### 完成记录

完成记录说明某个账户最近一次完整执行成功某份路线的时间，存在 `User/Pulonia/accounts/<账户 ID>/route-completions.json`：文件含 `schema_version`（1）和 `completions` 列表，每条字段如下。

| 字段 | 内容 |
| --- | --- |
| `route` | 路线身份 |
| `completed_at` | 完成时间，UTC |
| `run_id` | 运行 ID |
| `task_address` | 节点地址 |
| `attempt` | 尝试次数 |
| `instance` | 执行实例键，如 `primary`、`webview:小号a` |
| `rule` | 记录时的刷新规则（如模式、小时数、材料、来源），只用于在总览里显示“记录时规则”；判定时使用当前规则 |

- 每个账户的每份路线只保留**最新一条**：成功时替换旧条目，判定也只看最新一条。
- 每次成功的明细保存在对应运行历史的“本次完成的路线”`route_completions` 中，与完成记录同一结构。完成记录不承担历史职责。
- 不检查和未识别的路线成功后同样写入。完成记录没有过期清理，每个账户最多 10 万条。
- 与账本条目相比，去掉了 `scope_key`、`effect_key`、`event_key`、`window_key`、`units`、`next_eligible_at`（D19 随之完成）。
- **读取**：`IPuloniaAccountService.ListRouteCompletionsAsync(accountId)`。各实例按文件修改时间缓存账户进度，在运行开始时、地图追踪节点判定 CD 前、页面每分钟刷新时比较修改时间，有变化才重新读取。读写不经过 IPC。
- **清除记录**：`IPuloniaAccountService.ClearRouteCompletionsAsync(accountId, routes)` 在 `.writer.lock` 内读改写，删除指定路线的完成记录，不会覆盖其他实例刚写入的记录。任一实例的界面都可以清除；运行历史中本次完成的路线不变；不能撤销。“标记为已采集”不提供（D18）。
- **账户进度变化通知**：新完成记录落盘或清除记录后，本进程立即触发 `AccountProgressChanged`，界面据此重新读取，不在每次 `RunChanged` 时重建。其他实例的写入靠修改时间比较发现，页面最多延迟 1 分钟显示。
- **运行预览**：`IPuloniaTaskService.PreviewAsync` 与提交共用 `PrepareRunAsync` 准备快照（只读打开已保留归档），不写 `state.json`、不入队；按执行顺序对每个叶子调用 `GetStatus`，并预测“与前面同一路线，前一项成功后跳过”。

运行预览、任务树 CD 标记和路线 CD 表单按下表选择账户，日切时区取该账户的服务器时区：

| 计划的运行账户设置 | 显示的账户 |
| --- | --- |
| 指定账户 | 该账户 |
| 跟随当前账户 | 本实例当前账户 |

账户目录有多个账户时，页面顶部显示“CD 按账户：乙 ▾”，可以临时切换查看其他账户。这个选择只影响本页面的显示，不修改计划和实例设置。实际运行以运行开始时确定的运行账户为准。

界面呈现见[界面 · 路线 CD](user-interface.md#路线-cd)。

## 存储

### 文件组织

```text
User/Pulonia/
├─ plans/<planId>.json              计划；保存时留 .bak
├─ profiles/<profileId>.json        设置方案（共享设置）
├─ plan-order.json                  计划列表顺序（编辑器元数据）
├─ plan-view-state.json             节点折叠状态（编辑器元数据）
├─ accounts.json                    账户目录
├─ account-images/<账户 ID>-<yyyyMMdd-HHmmss>.png   账户标识图片，每次新建
├─ accounts/<账户 ID>/
│  ├─ route-completions.json        完成记录
│  ├─ boss-rewards.json             首领讨伐累计领奖次数
│  └─ run.lock                      账户占用（运行期间打开）
├─ instances/<实例目录名>/
│  ├─ settings.json                 实例当前账户
│  ├─ state.json / state.json.bak   实例运行状态（见下文）
│  └─ online.lock                   在线标记（实例运行期间打开）
├─ history/<planId>/<runId>.json    已结束运行的不可变记录，所有实例共用
├─ imports/<yyyyMMdd-HHmmss>.txt    旧配置导入报告
├─ .writer.lock                     跨进程写锁
└─ ScriptResources/                 仓库注册、保留归档、预览与 JS 工作目录
```

实例目录名：主实例为 `primary`，桌面分身为 `child_session`，云原神实例为 `webview-<小写实例名>`，见[统筹设计 6.1](../instance-account-model.md#61-实例键)。ID 与文件命名规则见[标识与磁盘路径](identifiers-and-paths.md)；`ScriptResources` 见[脚本仓库与任务资源](repository-resources.md)。

根目录不再有 `state.json`、`state.json.bak` 和 `boss-rewards/`，旧文件不转换，见[统筹设计第 11 节](../instance-account-model.md#11-迁移)。

所有写入先写同目录临时文件 `~<8 位>.tmp` 并刷新到底层存储，目标已存在时用 `File.Replace` 替换（同时保留 `.bak`），首次建立时移动；读取以 `FileShare.Read | FileShare.Delete` 打开，替换期间已打开的句柄继续读旧版本。`PuloniaTaskStore` 的写入还持有 `.writer.lock`，防止多个进程交错写入。子实例会写 `User/Pulonia`，所以 `.writer.lock` 和账户目录的修订号保留（D15）。

`run.lock` 与 `online.lock` 是互斥用的锁文件，分别在运行占用账户期间和实例运行期间以“允许他人读、不允许他人写”的方式打开；`run.lock` 写入实例键、运行 ID 和开始时间。进程退出时由系统释放句柄，崩溃不会留下占用。规则见[多账户](accounts.md)。

### 配置类数据

计划、设置方案、账户目录、计划顺序、折叠状态和仓库注册只需要“原子替换 + 后写者胜”。计划和账户目录另有修订号，保存旧修订时报冲突，两个页面共用同一编辑会话，这项检查成本很低。配置在运行开始前固定进快照，不同配置文件不要求同步提交。

损坏的计划文件不阻断其他计划：`ListPlansWithFailuresAsync` 跳过坏文件并返回失败清单，文件保留在磁盘上。编辑会话加载时弹出提示；调度保留读取失败计划的触发游标；有计划读不出时拒绝删除账户。预设列表遇到损坏文件仍直接报错。

以下两类数据不是配置，也不进入计划和快照，写入方式不同：

- **实例设置** `instances/<实例目录名>/settings.json` 只保存实例当前账户 `current_account_id`。由该实例写入，主实例也可以修改子实例的设置，不经过 IPC；原子替换，后写者覆盖。修改立即保存，正在运行的任务不受影响，下一次运行开始时生效。
- **账户进度** 在 `accounts/<账户 ID>/` 下：完成记录 `route-completions.json`，以及首领领奖次数 `boss-rewards.json`（键为计划 ID、节点 ID、重置批次，值为次数，按运行账户记录）。任意实例都可以写，在 `.writer.lock` 内读改写并耐久替换，不丢其他实例的更新。删除账户时一并删除它的账户进度。

### 实例运行状态

每个实例的运行状态存在 `User/Pulonia/instances/<实例目录名>/state.json`，是本实例队列和活动运行的唯一当前依据，格式版本 7：

| 字段 | 内容 |
| --- | --- |
| `schema_version`、`sequence` | 格式版本；每次保存递增的序列 |
| `pending_requests` | 本实例已固定快照、尚未开始的运行记录 |
| `active_run` | 本实例唯一的活动运行 |
| `pending_archives` | 已结束但尚未确认写入历史的运行 |
| `trigger_states` | 每个实例都有，只含本实例负责的定时触发器的游标，按（计划、触发器）记录，见[触发与热键](scheduling.md#游标) |

实例运行状态不含完成记录，账户进度见[按账户存放](#按账户存放)。

**唯一写入入口**是本实例的 `PuloniaTaskRunStateStore.MutateAsync`：在状态门内复制当前状态（只复制集合，写时复制）→ 应用修改 → 序列化一次并按读取规则自检 → 耐久替换 → 提交为新的当前状态。保存失败时内存保持上一版本并熔断，之后本实例拒绝新提交、停止自动运行。只读查询直接读已提交的状态，不加锁，也不为每秒的调度检查克隆整份状态。其他实例只读取这份文件（执行记录页显示排队和运行中的运行），不写入。

以下变化各自在一次替换中完成：请求入队与触发游标前移；运行开始；指定账户的核验 UID 与“切换账户”节点结果；节点结果（地图追踪成功时连同本次完成的路线，完成记录已按[写入顺序](#防止重复执行与崩溃后的误判)先写入账户目录）。当前执行节点的地址只在内存中更新，不单独写盘。

**读取**：只接受格式版本 7，其他版本报错并提示删除本实例的 `state.json` 与 `state.json.bak`；不转换旧文件，见[统筹设计第 11 节](../instance-account-model.md#11-迁移)。开发期也不剔除已停用字段，未知字段一律按严格读取报错。历史文件同样按当前格式严格读取，读不出的文件被跳过并提示。

**备份回退**：正式文件损坏时从 `.bak` 恢复，启动提示“已从备份回退”，下一次保存直接替换正式文件而保留这份有效备份（由加载时记录的标志决定，不再回读旧文件）；两份都无法读取时停止本实例的自动运行，保留文件。备份回退不能证明丢失时间段内没有游戏操作。集合上限为 1 万项。

实例运行状态是一份文件的替换，不是多文件事务。完成记录与节点结果分在两个文件，只靠固定的写入顺序保证崩溃后不重复执行。

### 历史

历史目录 `history/<planId>/<runId>.json` 由所有实例共用，每个实例只写自己的运行，运行 ID 不重复。运行结束时先放进本实例的 `pending_archives` 并保存，再按运行 ID 幂等写入历史文件（同一运行已存在且内容不同时拒绝覆盖），成功后从状态移除。中途崩溃时启动后按同一运行 ID 重试归档。历史读取不参与 CD 判定，历史保存失败也不会让任务重新执行。

- 运行记录增加 `instance`（执行实例键）、`account_id`（运行账户）、`account_source`（`instance_current` 或 `specified`）和 `uid_check`（跟随当前账户时为 `matched`、`mismatched` 或 `skipped`，不一致时另记读到的 UID；指定账户时为空）。`verified_uid` 只在指定账户时有值。本次完成的路线写在 `route_completions` 中。
- 任一实例的执行记录页都显示全部实例的运行：已结束的运行从历史目录读取，排队和运行中的运行只读各实例的 `state.json`。
- 启动时读取全部历史；读不出的历史文件被跳过，文件不删除也不改写，并通过 `RecoveryNotice` 提示（最多列出 3 份）。
- 常驻内存的历史只保留摘要（去掉快照正文），快照在首次查看详情或续跑时从历史文件按需读取。
- 历史文件不自动清理，保留数量策略待定。

收尾保存使用独立且有时间上限的取消控制（15 秒），不复用已经取消的任务令牌。UI 进度可以合并刷新，运行开始与结束、完成记录和节点结果必须等待保存完成。

### 依赖选择

| 选择 | 结论 |
| --- | --- |
| SQLite / ORM | 不引入，使用上述 JSON 存储 |
