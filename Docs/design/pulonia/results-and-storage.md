# Pulonia：结果证据、CD 与文件存储

[返回总览](../automation-system.md) · [用户故事](requirements.md) · [开发与验收计划](development-plan.md)

明确什么时候算完成、什么时候可重做，以及如何用 JSON 保存一致的进度和账本。不引入 Quartz、SQLite 或 ORM。

## CD、周期次数和“成功”的处理

### 三个问题分别回答

| 问题 | 由谁处理 | 示例 |
| --- | --- | --- |
| 什么时候发起？ | `PuloniaTaskTrigger` | 每天 20:00 |
| 现在能不能开始？ | 准入与节点条件 | 电脑空闲、指定账号可用、今天开放 |
| 这个资源现在能不能再做？ | 能力规则 + `PuloniaTaskLedgerEntry` | 此点位未刷新、周奖励已领、今日上限已到 |

“每周跑一次”是执行偏好，“某奖励每周只能领取一次”是游戏事实。这两类规则需要区分；只有击败某敌人也不等于领取了奖励。

### 资源规则

首版 `PuloniaTaskAvailabilityRule` 支持 `Unrestricted`、`RollingCooldown`、`ResetQuota` 三种；一个能力可有多条规则，例如独立的奖励资格与共享次数额度。

- 滚动 CD：从已确认的采集/领取发生时间计算 `NextEligibleAt`。例如某资源规则设为 48 小时，这是示例参数，不代表所有采集物规则。
- 周期额度：按服务器对应日历计算 `WindowKey`，保存本周期已消耗数量。每日、每周、每月及其他游戏周期由内容数据描述，不能统一写成“过去 24 小时”。
- 开放日：是日历条件，不能混同 CD。优惠次数、奖励次数、树脂和物品数量也是不同约束。

时间统一存 UTC；周期边界按账号服务器配置转换。优先记录奖励/采集发生时刻，而非整条长任务的开始或结束时刻。跨边界但无法确认事件属于哪一期时保留不确定状态并核验，不猜测为新周期成功。

### 去重键与作用域

```text
ScopeKey = 服务器 + 账号 UID                  // 账号奖励
ScopeKey = 服务器 + 世界拥有者 UID            // 世界采集物，联机时尤其重要
EffectKey = 稳定活动/资源/点位 ID
WindowKey = 规则对应周期起点，滚动资源则使用其活动状态
```

默认 CD 跟随实际资源，不跟随计划名、节点 ID、文件路径或脚本文件哈希。路线重命名、复制到另一计划、更新代码都不应清空同一资源的 CD。

精度分级：有点位 ID 和确认事件时按点位记；旧路线只能按稳定路线 ID 估算，并明确显示“路线级估计”。两条不同路线可能采同一批点位，没有覆盖关系元数据就无法准确去重。首版保留这个限制，后续给精选路线补 `ResourceCoverage`，不能宣称路线级 CD 已完全解决重叠。

### 完成合同

`PuloniaTaskOutcome` 区分 `Succeeded`、`ExecutedUnverified`、`PartiallySucceeded`、`Failed`、`Cancelled`、`Skipped`、`NeedsAttention`，并附机器可读原因、证据、产出和已确认副作用。

| 场景 | 可以确认什么 | 账本处理 |
| --- | --- | --- |
| Shell 退出码为 0 | 进程按约定成功 | 可标记 Shell 能力成功，不推出游戏资源完成 |
| 路线走到终点 | 路线执行结束 | 没有采集证据时只能估计，不能宣称全部物品到手 |
| 奖励界面确认、领取状态变化 | 指定奖励已领取 | 更新对应周期额度 |
| 拾取提示/计数变化/点位确认事件 | 已观测的采集事实 | 记录对应资源；批量计数变化不自动推断每个点位都成功 |
| 老 JS 正常返回 | 脚本执行结束 | 默认 `ExecutedUnverified`；可选执行频率限制，但与资源事实分开 |
| 执行 10 个点位后失败 | 10 个已确认点位完成 | 已完成部分保留 CD，剩余部分仍可执行 |

新 JS 和 C# 可报告结构化完成事件；内置高价值动作增加独立后置核验。脚本作者声明、视觉核验和人工确认要保留来源差异。精选托管模板对消耗额度的动作要求更可靠的完成合同。

针对 US-03、05，内置能力向调用者返回明确原因，例如“未能进入钓鱼界面”“背包空间不足”“树脂不足”“奖励已领取”；调用者不必解析日志判断是否记 CD。通过 JS 调用的路线与直接运行的路线进入同一结果/额度路径。子步骤已经提交的完成事件，父节点只能汇总引用，不能再次计入消耗；路线声明的预期怪物数也不冒充实测击杀数。

### 防止重复执行与崩溃后的误判

1. 任务服务串行检查额度，在同一份 `state.json` 中保存当前操作意图和占用，保存成功后才执行可能产生副作用的动作。
2. 每条确认事件带稳定 `EventKey`。将证据、对应额度变化和节点进度作为一次状态更新保存；重试提交相同事件不能重复计数。该路径直接等待写入完成，不经可延迟丢失的进度事件。
3. 执行中已确认的局部副作用立即记录，不等整个计划完成才保存。
4. 程序崩溃后，遗留运行与占用转为 `Interrupted/Uncertain`，不能按租约过期直接当成从未执行。
5. 先核验游戏当前状态，再决定补记成功、释放占用或重新执行。无法核验的领取/购买/消耗动作进入待处理；可重复且无业务风险的动作才允许自动重跑。

游戏操作与本地文件无法同时提交，因此不能承诺任意任务严格“只执行一次”。需要通过执行前意图、完成证据和不确定态处理缩小重复窗口。文件损坏或写入失败时停止自动推进；不能把损坏的账本重置为空后继续刷取。

用户可以查看“上次确认时间、来源、剩余 CD、下一次可执行时间”，也可以人工校正“游戏外已经采过”。程序未观察到的手动操作不能自动知道；缺少相关信息时显示未知。

默认遇到 CD 跳过当前节点并继续后续任务。需要等 CD 的请求释放资源后重新排队，并设置截止时间，不能让整个一条龙原地等待几小时。人工强制尝试只忽略执行偏好或估计限制，不伪造游戏奖励资格、不清空历史。

## 存储与第三方库

明确不引入 Quartz、SQLite、EF Core，也不实现一套自制数据库或通用事件溯源框架。沿用 d-v3 的 JSON 文件方向，用单主实例、单写入者和完整文件替换解决当前本地串行场景。

### 文件组织

```text
User/Pulonia/
├─ plans/<planId>.json              # 元信息、root_task、触发器、账号绑定
├─ presets/<presetId>.json          # 可选共享预设
├─ accounts/<accountId>.json        # 账号资料；托管阶段含目标与最近状态快照
├─ state.json                      # 队列、调度游标、活动运行、CD/额度、待归档运行
├─ state.json.bak                  # 上一个有效状态版本
└─ history/<planId>/<runId>.json    # 已结束运行的不可变快照及节点结果
```

文件用稳定 ID 命名，名称只用于展示。计划重命名不改变引用和历史位置。`PuloniaTaskStore` 返回模型，ViewModel 只负责编辑；新文件用 Newtonsoft.Json、UTF-8 无 BOM，既有文件仍按原格式导入。

配置文件可分别保存，但运行时在开始前将用到的计划、预设、账号绑定与资源版本固定进 `ActiveRun.Snapshot`。不同配置文件不要求同步提交，实际用的是哪一版在快照中可追溯；调用者不能边执行边改这份快照。

### 关键状态只保存一次

`state.json` 是调度、运行进度和 CD 的唯一当前依据，以下变化在内存中一次完成，再保存成一份文件：

- 到期请求入队与调度游标前移。
- 请求出队与活动运行建立。
- 执行前操作意图、账号身份、资源占用。
- 完成证据、额度消耗、事件去重键与任务进度推进。

首版一个主协调器拥有状态写权限；已有多实例通过 IPC 提交请求，不能各自直接改这个文件。写入流程为：在状态锁下基于旧版本生成候选状态 → 写同目录临时文件并刷新 → 完整替换正式文件并留备份 → 更新内存可见版本 → 释放锁。保存失败则不提交候选状态、不推进下一动作；游戏操作期间不持有状态锁。

可以使用 `File.Replace` 替换已存在文件并保留备份，首次建立文件使用同目录移动。重要写入显式刷新到底层存储；不能把只完成内存缓冲的异步写入等同于耐久落盘。这些系统 API 不能消除磁盘故障、突然断电或外部游戏操作的不确定性。[File.Replace 文档](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace?view=netframework-4.8)、[.NET 文件 I/O 说明](https://devblogs.microsoft.com/dotnet/file-io-improvements-in-dotnet-6/)

这是一份状态文件的替换，不是多文件事务协议。不要把进度写到一处、CD 写到另一处，再依赖后台事件碰巧同时保存。

### 历史、故障恢复与写入频率

运行结束时先将完整结果放进 `PendingArchives` 并保存状态，然后写对应的历史文件；历史文件写成功后，再从状态移除待归档项。中途崩溃可以按同一个 RunId 重试归档。历史读取不参与 CD 判定，历史保存失败也不能导致任务被重新执行。

启动时校验格式、版本和内容，优先读取正式状态；只能从备份恢复时，必须显示回退并核验遗留运行/未决操作。两份都无法读取时停止自动运行，保留文件，不把状态清零继续。备份回退不能证明丢失时间段中没有游戏操作。

UI 进度、当前坐标等可合并刷新；任务开始/结束、消费或领取确认、取消和关键断点必须等待保存完成。收尾保存使用独立且有时间上限的取消控制，不能直接复用已经取消的任务令牌。关键完成事件不依赖 UI 订阅者；UI 的更新异常不改变业务结果。

配置编辑保留自动保存体验，但拖拽和批量添加只保存一次，普通字段编辑防抖；显示“保存中/保存失败”，失败后保留编辑内容。文件替换只保护完整性，防抖和单写入者才解决重复写与旧快照覆盖问题。

`state.json` 只保留当前队列、活动运行、未归档结果和仍有效的 CD/额度；不塞入全部历史、完整日志或图片。历史可按数量清理，但不能删除仍约束当前执行的额度状态。若实测证明全文件写入成为瓶颈，再讨论局部优化，不预先引入 WAL、索引树或数据库。

### 依赖选择

| 选择 | 建议 |
| --- | --- |
| SQLite / ORM | 不引入，使用上述 JSON 存储 |
| Quartz / Hangfire / Elsa | 不引入，.NET 定时循环足够承担本机触发检查 |
| Cronos | 当前不新增；确需高级 Cron 时再单独评估，不能为替换 Quartz 顺带引入另一套调度框架 |
| .NET 的 `PeriodicTimer`、取消令牌、锁、文件 API | 用于调度检查和单写入者；不增加第三方依赖 |
| Newtonsoft.Json | 复用项目已有依赖 |
| Windows 任务计划程序 | 使用系统能力负责应用不在运行时的启动，无需引入大型调度平台 |
| WPF-UI、MVVM Toolkit、Behaviors、gong-wpf-dragdrop | 沿用现有 UI 技术 |
| ClearScript、现有识别/状态机/运行环境 | 封装复用，移除对页面和全局运行状态的依赖 |
| Roslyn、通用规则引擎、新状态机库 | 首版不需要 |

当前方案不要求新增第三方库。时间规则边界、关键文件写入和恢复是需要验证的实现内容，不能因为没有框架就省略这些语义。
