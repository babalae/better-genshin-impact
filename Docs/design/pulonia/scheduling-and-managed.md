# Pulonia：触发、托管与多账号

[返回总览](../automation-system.md) · [用户故事](requirements.md) · [开发与验收计划](development-plan.md)

调度决定何时发起请求，托管决定做什么，多账号决定为谁执行；三者复用同一任务服务。

## 程序内定时与热键运行

### 调度语义

- 用户设置一次性、每日多个时刻、每周指定日期、每月指定日期或固定间隔；简易表单生成唯一五段数字 Cron，也可编辑高级表达式。一次性时刻和固定间隔另存锚点。`TimeZoneId` 明确时区，定时的时区与游戏服务器刷新时区可以不同。
- 定时与热键都生成请求，不直接调用截图器或页面命令。一个触发器可选择整个计划或子树；单动作快捷方式内部也是一个小计划。
- 多账号绑定展开为有序请求，使用同一个 `BatchId`。默认一个账号完整执行后再处理下一个，减少频繁切号。
- 定时请求使用 `(TriggerId, OccurrenceUtc, AccountId)` 去重，入队与推进调度游标在同一次 `state.json` 保存中完成。恢复后重复扫描不能创建重复请求。
- 同一计划、同一账号已有活动请求时，自动触发默认合并或跳过并记录原因；热键默认不重复排队，可配置排队一次。
- 不同计划同时到期默认排队。针对“到点改跑每日计划”的需求，可显式选择“停止当前运行后执行”，但必须等待取消与资源释放成功；无法停止时显示受阻，不能同时驱动游戏。
- 补触发默认“有效时间窗内合并补一次”，而不是把关机数天漏掉的每日任务全部补跑。过期显示为过期，不计成功。
- 真正启动前重新检查触发器是否仍启用、配置是否改变以及是否超过截止时间；旧配置或过期请求归档，不执行任务。
- 不检测用户活动，也不区分用户输入与模拟输入。手动取消、总时限和“停止当前”策略仍使用现有取消及资源释放流程。

应用内采用一个 `PeriodicTimer` 循环（例如每秒检查一次）计算到期项并提交请求；使用一个异步消费者避免重复回调，执行任务在独立的串行消费循环中进行，不能阻塞调度检查。定时器只负责通知检查，是否到期以持久化游标和当前时间判断，睡眠恢复时补检。[.NET 官方实现](https://source.dot.net/System.Private.CoreLib/src/runtime/src/libraries/System.Private.CoreLib/src/System/Threading/PeriodicTimer.cs.html)

时区规则明确为：夏令时缺失时刻顺延至第一个有效时刻，重复时刻每个日程只触发一次；本月不存在的日期默认跳过并在预览中显示。固定间隔以保存的锚点计算，不能按程序每次启动时间重置。时钟回拨结合游标去重，时钟前跳按漏触发策略处理。调度计算接受可注入的时间来源，便于验证这些边界。

d-v3 的 Quartz Cron 不直接复制：能等价表示的规则转换成当前五段数字 Cron；暂时不能表示的规则保留原文并标记待调整，禁止静默改变时间语义。支持数字、列表、范围和步长，不接受秒段及 Quartz 扩展；日和星期同时限制时取交集。Quartz 不作为备选引入。

### 程序运行边界与手动命令行

定时和全局热键仅在 BGI 主实例运行期间生效。程序关闭时不执行，也不由操作系统启动程序；用户重新启动后，按原日程、有效窗口和补触发策略处理遗漏时间。

保留 `--pulonia-run <planId>` 作为用户显式提交计划的手动命令行入口；程序已启动时通过单实例 IPC 转交主协调器，不另开执行实例，不经旧任务页提前启动截图器。此入口不是自动日程的启动机制。

## 自动托管与多账号

### 新手路径

选择账号 → 选择角色及目标练度/物品数量 → 选择运行时间 → 查看今日安排 → 一键托管。

内置任务目录按角色、材料、任务用途检索，并维护精选资源包。下载、依赖解析、版本锁定在后台完成，用户无需理解仓库订阅；缺失资源显示明确下载/不可用状态。底层脚本来源、版本和权限仍能在详情中查看。

规划器输入为 `PuloniaDevelopmentGoal + PuloniaPlayerSnapshot + 游戏规则数据 + PuloniaTaskDefinition + 账本`，输出仍是 `PuloniaTaskPlan` 的具体执行内容。

首版采用可解释规则：时限与用户优先级 → 今日可刷且有缺口的培养材料 → 日周月事项 → 剩余时间的可选采集。树脂等预算贯穿整个账号计划，不能每个目标独立分配一份总树脂。

可先生成“刷新账号状态”准备步骤，再在明确的规划阶段生成并冻结执行子树，记录“为何添加/跳过”。执行中发现状态变化时，仅在节点边界重新规划未执行部分，并留下新版本记录，不改写已执行节点。

不能依赖昨天的快照决定今天一定有多少树脂；花费前核验关键数量。读取不到材料数量不等于材料为 0。游戏规则表、材料来源和开放条件需要版本维护，不能由调度器凭空推断。

物品目标必须明确口径：“库存补到 N”使用最新库存计算缺口；“本周期新采 N”使用该周期已确认产出；“角色培养到指定练度”从当前练度与目标重算剩余材料，再扣除可用库存。用户手动使用、合成或消耗材料后刷新相关状态，不能沿用旧总数持续补货，也不能用静态材料阈值假装已经完成角色培养。相关观测缺失时显示待刷新/待确认，不默认目标清零或无限刷取。这三种口径是目标上的字段，不各建一套规划系统。

天然树脂、浓缩树脂、补充道具及付费补充要有清晰的可用预算和用户选择，预算不足时换候选任务或结束。圣遗物随机收益和偏好意味着“最佳”应表达为“符合当前目标与预算的推荐安排”，并允许改优先级。

### 自动识别的实施边界

已有角色接口主要读取指定角色的属性/武器/天赋；背包计数主要面向目标物品。完整 box 枚举、全背包/圣遗物资产建模、装备评估和可靠增量更新仍需独立实现和验证。

分层落地：先用户选目标 + 扫描必要字段；再完善角色集合和物品缺口；最后扩展圣遗物与更复杂培养策略。这个顺序不影响同一执行引擎最终承接全部场景。

### 多账号流程

`计划 A × 账号列表` 展开后，按绑定顺序执行：准备账号 → 登录/切换 → 到达可核验界面 → 核对服务器和 UID → 执行计划 → 清空会话相关缓存 → 下一个账号。

新增 `IPuloniaAccountSwitcher`，由具体登录渠道实现；可以先支持手动登录确认，再覆盖已有登录态可自动选择的渠道。验证码、二次验证和失效登录态不能由引擎统一解决，遇到时阻塞该账号，按策略继续其他账号。

账号 UID、资源账本、状态快照、所选预设必须对应一致。不能在切号前把目标账号设置为“已登录”；登录失败时不能将上一账号的执行结果写到目标账号。

登录资料在需要持久化时使用 Windows 凭据存储/系统保护机制，计划只保存引用。BGI 多实例不是多账号状态模型；首版仍按交互会话串行切号，后续隔离桌面或真正独立输入环境再考虑并行。
