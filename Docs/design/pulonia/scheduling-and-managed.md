# Pulonia：触发、托管与多账号

[返回总览](../automation-system.md) · [用户故事](requirements.md) · [开发与验收计划](development-plan.md)

调度决定何时发起请求，托管决定做什么，多账号决定为谁执行；三者复用同一任务服务。

## 程序内定时与热键运行

### 调度语义

- 用户设置一次性、每日多个时刻、每周指定日期、每月指定日期或固定间隔；简易表单生成唯一五段数字 Cron，也可编辑高级表达式。一次性时刻和固定间隔另存锚点。`TimeZoneId` 明确时区，定时的时区与游戏服务器刷新时区可以不同。
- 定时与热键都生成请求，不直接调用截图器或页面命令。一个触发器可选择整个计划或子树；单动作快捷方式内部也是一个小计划。
- 多账号绑定展开为有序请求，使用同一个 `BatchId`。默认一个账号完整执行后再处理下一个，减少频繁切号。
- 定时请求使用 `(TriggerId, OccurrenceUtc, AccountId)` 去重，入队与推进调度游标在同一次 `state.json` 保存中完成。恢复后重复扫描不能创建重复请求。
- 同一计划、同一账号已有活动请求时，自动触发默认合并或跳过并记录原因；热键默认不重复排队，可配置排队一次。
- 不同计划同时到期默认排队。针对“到点改跑每日计划”的需求，可显式选择“停止当前运行后执行”，但必须等待取消与资源释放成功；无法停止时显示受阻，不能同时驱动游戏。
- 补触发默认“有效时间窗内合并补一次”，而不是把关机数天漏掉的每日任务全部补跑。过期显示为过期，不计成功。
- 真正启动前重新检查触发器是否仍启用、配置是否改变以及是否超过截止时间；旧配置或过期请求归档，不执行任务。
- 不检测用户活动，也不区分用户输入与模拟输入。手动取消、总时限和“停止当前”策略仍使用现有取消及资源释放流程。

应用内采用一个 `PeriodicTimer` 循环（例如每秒检查一次）计算到期项并提交请求；使用一个异步消费者避免重复回调，执行任务在独立的串行消费循环中进行，不能阻塞调度检查。定时器只负责通知检查，是否到期以持久化游标和当前时间判断，睡眠恢复时补检。[.NET 官方实现](https://source.dot.net/System.Private.CoreLib/src/runtime/src/libraries/System.Private.CoreLib/src/System/Threading/PeriodicTimer.cs.html)

时区规则明确为：夏令时缺失时刻顺延至第一个有效时刻，重复时刻每个日程只触发一次；本月不存在的日期默认跳过并在预览中显示。固定间隔以保存的锚点计算，不能按程序每次启动时间重置。时钟回拨结合游标去重，时钟前跳按漏触发策略处理。调度计算接受可注入的时间来源，便于验证这些边界。

d-v3 的 Quartz Cron 不直接复制：能等价表示的规则转换成当前五段数字 Cron；暂时不能表示的规则保留原文并标记待调整，禁止静默改变时间语义。支持数字、列表、范围和步长，不接受秒段及 Quartz 扩展；日和星期同时限制时取交集。Quartz 不作为备选引入。

### 程序运行边界与手动命令行

定时和快捷键仅在 BGI 主实例运行期间生效。程序关闭时不执行，也不由操作系统启动程序；用户重新启动后，按原日程、有效窗口和补触发策略处理遗漏时间。

快捷键复用现有 `HotKeySettingModel`、`HotKeyTextBox` 和 `HotKeyTypeEnum`：全局热键支持组合键 / 功能键；键鼠监听支持键盘单键 / 鼠标侧键，沿用现有功能启动、键鼠监听启用、游戏前台及聊天屏蔽规则，不另外安装监听钩子。点击类型按钮切换时清空原键值，重新捕获并校验后保存。`HotkeyType` 随触发器持久化；旧配置缺省仍是全局注册，并省略默认字段以保持旧配置签名，不能因此取消原有排队请求。

已有软件快捷键配置优先于计划注册，统一模型也检查已注册的跨类型冲突。键鼠监听不区分修饰键，因此监听 `F8` 与全局 `Ctrl+F8` 也视为冲突。注册失败显示原因，不能注销原功能或偷偷占用；主实例关闭时在所属 UI 线程统一释放两种模式，重复清理仍安全。

触发器列表卡片展示启用开关，切换后独立保存 `Enabled` 和配置生效时间，不提交右侧未保存的配置草稿，刷新列表也保留该草稿。新触发器先以禁用状态保存，再从卡片启用；启用“停止当前”策略仍需确认。写盘失败保持明确错误，不能声称调度器已经采用新状态。

保留 `--pulonia-run <planId>` 作为用户显式提交计划的手动命令行入口；程序已启动时通过单实例 IPC 转交主协调器，不另开执行实例，不经旧任务页提前启动截图器。此入口不是自动日程的启动机制。

## 自动托管与多账号

### 新手路径

首期体力计划采用绑定路径：选择账号与已有任务计划 → 选择近期培养目标、培养方面优先级与最终兜底 → 绑定方案 → 在任务支持的字段中选择“体力计划” → 查看本次预计安排 → 开始执行。一条龙也是任务计划，采用同一规则；全部计划默认不指定体力方案。

2026-10-12 确认的术语、字段来源组合、无状态规划、预计算与 UI / UX 以[体力计划设计](resin-plan.md)为准，本文保留托管和调度的整体边界。一个账号可保存多套方案；连续或嵌套执行使用输入方方案，子计划不自行替换。自定义树脂用量优先预留，托管只使用剩余资源。

绑定模式的规划器输入为体力方案、已有任务的有效配置与字段来源、实际账号状态和游戏规则，输出对应原任务的有效参数、执行段、树脂分配和解释。不会新增任务树节点、启用关闭的任务或改变顺序；缺少对应能力时显示不能承接的需求。预览与执行使用同一规划器，配置变化不自动操作游戏。

自动生成任务计划是后续能力，本期不提供。后续独立托管入口可以采用“选择账号 → 选择角色及目标练度/物品数量 → 选择运行时间 → 查看今日安排 → 一键托管”的完整路径；内置任务目录按角色、材料、用途检索并维护精选资源包，后台下载、依赖解析和版本锁定让用户无需理解仓库订阅。缺失资源仍需显示下载/不可用状态，来源、版本和权限可在详情中查看。该后续路径不改变当前绑定模式的能力边界。

首期角色培养默认同级，按培养方面分配预算，并优先考虑今日真正受轮换限制的目标材料。合并相同副本和兼容配置的需求，集中备齐有限目标，再安排最终兜底；长期圣遗物刷取不能阻塞其他有限目标。树脂预算贯穿整个账号计划，共享库存只扣除一次，不能每个目标独立分配一份总树脂。

账号状态刷新属于执行准备阶段，不写成新增任务节点。开始时固定配置与方案版本并刷新实际状态；执行中仅重算尚未执行部分，留下本次版本和原因，不改写已执行结果。每次新运行重新读取练度、库存和树脂，不按历史刷取次数、完成标记或轮转游标推算培养进度；单次运行记录只用于追溯。已有资源 CD 与活动资格仍由各自的规则核验。

不能依赖昨天的快照决定今天一定有多少树脂；花费前核验关键数量。读取不到材料数量不等于材料为 0。游戏规则表、材料来源和开放条件需要版本维护，不能由调度器凭空推断。

物品目标必须明确口径：“库存补到 N”使用最新库存计算缺口；“本周期新采 N”使用该周期已确认产出；“角色培养到指定练度”从当前练度与目标重算剩余材料，再扣除可用库存。用户手动使用、合成或消耗材料后刷新相关状态，不能沿用旧总数持续补货，也不能用静态材料阈值假装已经完成角色培养。相关观测缺失时显示待刷新/待确认，不默认目标清零或无限刷取。这三种口径是目标上的字段，不各建一套规划系统。

原粹树脂、浓缩树脂及补充道具分别计算用途、可用预算和用户选择，预算不足时换兼容候选或结束；原石自动补充不进入首期。方案资源偏好仅约束跟随方案的用量，自定义任务明确开启的道具按自身配置处理。圣遗物随机收益和偏好意味着“最佳”应表达为“符合当前目标与预算的推荐安排”，并允许改培养方面优先级。

### 自动识别的实施边界

已有角色接口主要读取指定角色的属性/武器/天赋；背包计数主要面向目标物品。完整 box 枚举、全背包/圣遗物资产建模、装备评估和可靠增量更新仍需独立实现和验证。

分层落地：先用户选目标 + 扫描必要字段；再完善角色集合和物品缺口；最后扩展圣遗物与更复杂培养策略。这个顺序不影响同一执行引擎最终承接全部场景。

### 多账号流程

2026-10-10 用户确认首版为 PC 官服：每份新一条龙配置绑定一个账号，缺省使用免配置的“默认账号（当前登录账号）”。服务器和渠道不作为账号界面的必填设置。账号准备为服务级前置阶段，默认隐藏；启用多账号显示后固定于清单首位，但不写入隐藏节点。流程为准备账号 → 图片/OCR/可选密码登录 → 完整核验 UID → 执行计划；默认账号不主动登出，相同 UID 已登录时直接采用当前登录态。

接口为 `IPuloniaGenshinAccountSwitcher`，将 `AccountSwitchStateMachine` 的图像状态机与 `SwitchAccountMultipleMode` 的列表 OCR、密码及验证码识别移植到 C#。UID 要在连续两次新截图中完整一致，不采用相似度判定。操作共用输入所有权和取消令牌，响应等待/轮询 500ms，总准备预算 180 秒、最多两轮；验证码、二次验证、明确密码错误和失效登录态进入待处理。10.1 状态以开发计划为准，真实切号效果待用户验收。

账号 UID、资源账本、状态快照、所选预设必须对应一致。不能在切号前把目标账号设置为“已登录”；登录失败时不能将上一账号的执行结果写到目标账号。

登录资料在需要持久化时使用 Windows 凭据存储/系统保护机制，计划只保存引用。BGI 多实例不是多账号状态模型；首版仍按交互会话串行切号，后续隔离桌面或真正独立输入环境再考虑并行。

### 多配置一条龙与定时接管（步骤 10.2 待实现）

“更多 → 连续运行”通过窗口勾选已有一条龙计划并排序，支持同账号多个配置和多个账号各自配置。具名批次复用既有日程、Cron、热键、去重和繁忙规则。批次作为一个队列项执行，成员保留独立快照、实际 UID 和历史；切号失败释放输入后处理下一个。批次触发一次，不调用成员自己的触发器。

**任意保存批次至少存在一个启用的定时触发器时，其列表内成员的独立定时全部不生效。** 不改写成员原开关或日程，显示“已由批次定时接管”与批次名称；多个批次按集合合并接管。全部禁用/删除、删除批次或移除成员后，没有其他接管者才恢复，不补跑被接管期间时刻。仅热键或禁用的定时不接管；手动、热键、续跑不受影响。

调度每轮使用一致配置先计算接管，再提交到期请求；独立定时排队后的准入也复核，运行中的请求不强停。批次入队与游标共用耐久提交；整批开始前检查窗口和配置，开始后使用固定快照，后续成员不因开始窗口到期跳过。不自动恢复中断批次，不新增系统定时启动。
