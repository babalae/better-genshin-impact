# Pulonia 多仓库设计建议

状态：早期多仓库讨论草案。直接读取远程仓库、固定来源版本及可写工作目录现已实施，实际合同见[远程仓库资源读取](repository-resources.md)。本文中的本地开发来源管理、来源筛选和调试界面仍为后续设想；与实际合同冲突的订阅目录、旧 API 映射和实施顺序不再作为当前实现依据。

[任务模型](task-model.md) · [界面设计](user-interface.md) · [迁移设计](migration.md) · [领域术语](../../../CONTEXT.md)

## 设计目标

普通用户可以直接使用官方资源；需要第三方资源时，添加来源后即可与现有脚本一起使用；开发者可以直接注册自己的工作目录，远程更新不会覆盖它。一个计划允许同时引用多个仓库，同名资源互不替换。

统一资源选择入口，分别管理文件所有权。任务始终明确引用来源，仓库筛选、列表排序和默认浏览来源均不改变既有任务的运行目标。

当前落地语义统一为“本机仓库副本”“同步仓库”“刷新目录”“任务使用版本”和“更新任务资源”。添加任务只读取本机内容；同步仓库不修改计划，一键同步并更新只处理普通计划与新一条龙实际引用的仓库。本文后续出现的“仓库订阅”仅描述老配置组或早期设想，不是 Pulonia 新界面的操作名称。

## 当前实现的边界

- `ScriptRepoUpdater.CenterRepoPath` 根据所选渠道解析当前远程仓库，订阅记录已经按仓库目录分别保存。
- `ScriptRepoUpdater.PathMapper` 仍把不同远程来源安装到共用的 `User/JsScript`、`User/AutoPathing` 等目录。来源隔离尚未贯穿安装内容。
- `PuloniaTaskResourceCatalog` 按任务类型和单个资源根目录建立索引；资源描述与任务路径尚未包含仓库身份。
- `PuloniaTaskBuilder` 通过 `ResourceBaseDirectory` 解析相对路径，资源专用参数作用域也使用当前资源 ID / 路径匹配。
- `PuloniaJavaScriptTaskExecutor` 显式限制 JS 项目必须位于 `User/JsScript`；`ScriptProject` 构造逻辑也依赖该全局目录。
- `AutoPathingScript.RunFileFromUser` 等旧脚本 API 使用全局资源目录。只改任务执行器仍不足以隔离脚本内部依赖。
- 已有设计要求任务固定资源指纹、更新后显式确认，且不能在缺少旧内容时承诺精确续跑。本方案保留这些约束。

## 分类与所有权

界面提供三种容易理解的来源，但底层仅需要两种内容管理方式。

| 用户看到的来源 | 内容由谁维护 | 获取新内容的方式 | 典型操作 |
| --- | --- | --- | --- |
| 官方仓库 | 远程发布方，程序管理本机副本 | 同步仓库 | 浏览、添加任务、查看更新 |
| 第三方仓库 | 远程发布方，程序管理本机副本 | 同步仓库 | 添加地址、浏览、独立同步 |
| 本地脚本 | 用户 | 导入文件或直接编辑 | 打开目录、刷新、添加任务 |
| 开发工作目录 | 开发者 | 编辑器、Git 等开发工具 | 引用目录、试运行、打开编辑器 |

“官方 / 第三方”是发布方身份；“远程托管 / 本地目录”决定程序能否更新文件；“开发用途”决定是否展示调试操作。三者不能揉成一个互斥枚举。官方标识应由应用认可的来源映射产生，第三方清单不能自行声明为官方。

本地目录即使包含 `.git` 或配置了 Git remote，也仍是用户管理的目录。程序不自动 pull、reset、clean，也不把它加入远程更新目标。

默认提供官方仓库和“我的本地脚本”。开发工作目录可以添加多个。添加本地目录时默认直接引用，导入到“我的本地脚本”则明确表示复制；两种动作不能共用含糊的“添加”行为。

## 用户操作流程

### 添加任务

保留当前“先选任务类型，再进入资源选择弹窗”的交互，增加来源筛选，不新增独立任务库页面。

```text
添加 JS 任务

来源：[全部已安装资源 ▼]    [搜索脚本……]    [刷新]

自动采集       官方仓库          已安装
自动采集       某作者的脚本      已安装
自动采集       我的开发目录      本地 · 开发

右侧：脚本说明、来源、版本状态、脚本参数

[管理脚本来源]  [获取更多资源]              [添加到计划]
```

- 单一来源时弱化筛选控件；多个来源时显示仓库名称。名称、作者、目录和来源均可参与搜索。
- 路线等目录树按仓库分组，不把多个仓库的同名目录合并成一棵实际目录树。
- 同名资源保留多条结果，既不静默覆盖，也不根据优先级决定执行哪一个。
- 搜索范围默认是已安装资源及本地目录；“获取更多资源”进入远程目录，完成获取后回到当前选择流程。
- 任务树可以用紧凑来源标签展示第三方和开发资源，详情始终可查准确仓库与相对位置。
- 搜索结果到添加任务之间若发生更新，最终确认应重新核对所选资源版本，不能使用另一个仓库或版本代替。

### 管理脚本来源

入口放在资源弹窗与设置中，复用同一管理视图。每项显示名称、来源地址或本地位置、更新状态和引用情况。

- 远程来源提供“同步仓库”。不同仓库可分别同步，一项失败不影响其他来源；同步不修改任务使用版本。
- 本地来源提供“打开目录”“刷新”“重新定位”，开发用途额外提供试运行相关选项。
- 连接失败且已安装内容可用时保留离线运行；显示下载失败，不把已安装资源误标为消失。
- “暂停自动更新”不影响已有任务运行；“隐藏于添加列表”也不改变引用解析。若提供彻底停用功能，应明确它会阻止相关任务运行。
- 移除来源之前显示受影响的计划；移除后保留失效引用和修复入口，不能自动改绑同名资源。移除本地来源仅取消注册，不删除用户目录。
- 远程地址更换若只是已确认的同一来源镜像，可以更新连接信息；若实际更换发布者，应添加新来源。迁移任务通过显式“替换资源来源”完成。

### 开发者调试

推荐第一版采用独立开发来源与独立调试计划：注册工作目录 → 在该来源选择脚本 → 试运行当前文件。无需先复制到 `User/JsScript`。

正式任务继续采用固定版本规则；“试运行当前文件”是显式运行操作，在每次开始时重新读取文件并记录实际指纹，不要求开发者每次手工更新计划固定值，也不修改其他正式计划。

直接从工作目录运行时，运行期间编辑文件可能影响后续读取，不能宣称获得了不可变内容快照或可以精确恢复。可检测变化时提示停止后重跑；需要严格复现时另用内容快照运行。调试入口明确区分“重新运行当前文件”和“继续旧运行”。

后续确有需要再提供会话级资源替换：显式选择“本次用工作目录中的脚本替换某个任务资源”，记录原引用与实际引用，结束调试后失效。不能让本地同名脚本自动抢占官方脚本。

## 身份与引用

### 仓库注册

仓库注册至少保存：稳定的本机仓库 ID、显示名称、管理方式、连接信息或目录位置、按资源类型划分的根目录、更新偏好、开发用途标记。

- 本机仓库 ID 与展示名称、磁盘位置分离；改名与重新定位不改变已有任务引用。
- 一个仓库可以包含多种资源类型。本地用户可以直接选择 JS 项目集合目录或路线目录，不强制重组为远程仓库的目录布局；遇到未知布局时由用户指定资源类型及子目录。
- 远程源身份与本机注册 ID 分离。导出计划携带不含凭据的来源描述，用于在另一台机器解析或建立对应注册；本机绝对路径不作为可移植身份。
- 不同分支/发布频道如需并存，应建立独立的内容选择或注册，不能让同一任务引用随全局频道设置改变。镜像只是已确认同一来源的传输地址。

### 任务资源引用

最低可行身份为“仓库 ID + 资源类型 + 仓库内相对路径”。任务类型已经保存在节点上，不需要再添加第二个可发生矛盾的类型判别字段。

建议格式示意，字段尚未定稿：

```json
{
  "id": "task-collect",
  "name": "自动采集",
  "task_type": "javascript",
  "resource": {
    "repository_id": "repo-author-a",
    "path": "自动采集"
  },
  "resource_version": "sha256:..."
}
```

这里 `path` 相对该仓库的 JS 资源根目录。绝对运行路径由解析器产生，不由任务保存为主要身份。旧 `path` 格式经迁移转换；转换后只有一个权威定位字段。

现有 `PuloniaTaskSource` 表示分组的目录或计划来源，不应同时承担仓库管理对象。目录引用应复用相同的仓库定位值对象；计划引用仍按 PlanId 定位。

资源专用预设、参数覆盖、索引缓存和资源详情都使用带仓库身份的键，避免第三方同名脚本复用错误参数。任务节点 ID 仍独立于资源身份；游戏副作用的 CD / 额度作用域也不能因为换仓库而自动重置。

第一版可接受资源在仓库内改路径后需要修复引用。以后仓库协议提供稳定资源 ID 时，再支持跨重命名定位，不预先建设复杂包管理系统。

## 文件、更新与版本

### 目录所有权

远程安装内容按仓库隔离，“我的本地脚本”有独立目录，开发工作目录保留在开发者选择的位置。计划、参数和运行记录继续位于用户配置区域。

```text
程序管理的资源区/
  <仓库 ID>/
    安装内容或版本缓存/

用户维护的本地脚本区/
  JS、路线等资源/

开发者自己选择的工作目录/
  项目源码/
```

远程更新器只接受已注册的程序管理目标，不接受任意绝对目录。注册和更新都检查目录的真实边界，拒绝与本地工作目录相同或相互包含的目标；Windows 大小写、目录分隔符、重解析点等不能绕过该边界。

“不会覆盖开发目录”是写入权限与所有权约束，不能仅依赖路径命名、界面开关或某次更新时跳过同名目录。

### 同步仓库与更新任务资源

同步仓库是“获取新内容到本机仓库副本”，更新任务资源是“让计划采用本机内容”，两者分开。

1. 在独立临时位置下载与验证，只刷新对应仓库的索引。
2. 汇总哪些任务引用的内容变化，展示“3 个任务有可用更新”，支持批量查看和采用。
3. 采用时检查参数定义、依赖和目录清单差异；不兼容项需要处理，兼容项可以批量确认。
4. 保存更新后的计划引用与版本。正在运行的内容不被替换。

初期沿用当前指纹校验时，旧内容被更新且没有内容缓存就必须阻止旧版本运行；不能把“记录了 hash”写成“已经保存了旧版本”。建立按需版本缓存后，旧计划才能继续使用已保留的内容。只缓存实际选用的资源及其依赖，无需每个计划复制整仓。

运行与更新的最低保障是禁止更新正在使用的内容；跨进程实例也必须遵守。后续通过不可变版本目录与运行引用计数/租约实现并行下载、延迟清理。旧缓存仅在没有计划、运行或保留策略需要时才清理。

脚本可能写入项目文件，现有 `saved_files` 也有兼容需求。不可变代码缓存不能直接作为可写运行目录：新协议区分资源文件与可写用户数据；旧脚本需要兼容工作副本或暂缓纳入不可变缓存能力。迁移不能丢失已保存的用户数据，也不能把运行写入误认为发布版本变化。

### 脚本内部依赖

顶层任务与脚本内部读取必须共享明确的来源规则：项目内相对读取仍以项目为根；跨资源读取明确绑定仓库；没有显式绑定时不得搜索所有仓库并挑选第一个同名文件。

旧 `RunFileFromUser` 等 API 暂时固定映射到迁移时的兼容来源，保持原有语义，并在文档中写清；新 API 接收显式来源，或由声明过的依赖映射提供来源。依赖解析结果也进入本次版本记录。

## 迁移与实施顺序

### 第一阶段：身份贯通与本地调试

- 建立仓库注册和资源引用模型，资源索引聚合多个已注册根目录。
- 贯通创建弹窗、Builder、资源专用参数匹配、执行器和脚本项目加载，使本地开发目录真正可运行。
- 旧资源位置注册为兼容来源，原任务逐步迁移为明确引用；绝对路径不能猜成任意已知仓库。
- 旧目录可能混合下载内容与本地修改。无法证明来源的文件保持用户所有，不依据文件名或当前选中的远程仓库自动归属。
- 在本地/兼容目录承诺不被远程覆盖之前，必须同时切断旧更新器向该目录的写入。不能只改 Pulonia，新旧入口继续共享有覆盖风险的目标。
- 提供来源筛选、开发目录注册、显式试运行、失效引用重新定位。

### 第二阶段：远程来源隔离

- 将已有远程渠道迁为可并存的注册项，官方来源与第三方来源分别安装、订阅与更新。
- 根据订阅记录和内容核对提出迁移映射；存在歧义或本地修改时保留原文件，由用户决定是否改绑远程资源。
- 新远程下载进入专属目录；旧脚本 API 使用确定的兼容映射，不再从全局“当前仓库”推断来源。
- 增加更新影响清单、批量采用、移除来源影响分析、计划导入的来源映射。

### 第三阶段：版本缓存和高级开发体验

- 按需保留资源内容及依赖，满足固定版本运行、回滚和精确续跑的内容要求。
- 处理可写脚本数据与旧脚本兼容工作副本，再开放相应缓存能力。
- 增加目录变更监听与防抖刷新，保留手动刷新作为兜底。
- 根据实际需要增加调试会话临时替换、版本锁定界面等功能。

职责可收敛为仓库注册、现有资源目录索引、资源解析、远程更新四部分。先扩展已有类能承担的职责，不为每个数据对象增加接口或新的管理页面。

仓库注册、资源身份、解析和更新属于应用共享的脚本资源能力，Pulonia 是使用方。现有 JS 列表、路线管理、仓库页面及脚本内部 API 应逐步使用同一套来源规则，避免只有新任务页面支持多仓库、旧入口仍依赖全局目录。

## 验收场景

| 场景 | 预期行为 |
| --- | --- |
| 官方、第三方、开发目录有同名同路径脚本 | 可同时添加，执行各自绑定的来源 |
| 更新官方仓库 | 仅改动官方托管内容，不改动第三方、本地和开发目录 |
| 切换浏览来源或调整仓库列表顺序 | 已有任务的运行目标不变 |
| 开发目录关联了官方 Git remote | 仍不被程序自动更新 |
| 在编辑器改动开发脚本后再次试运行 | 使用当前文件并记录实际版本，无需重复确认正式计划版本 |
| 一个远程仓库断网 | 已安装内容可用，其他仓库正常使用 |
| 仓库目录迁移到另一块磁盘 | 重新定位后恢复引用，无需逐个重建任务 |
| 移除仍被任务引用的仓库 | 提示受影响计划，引用保留为失效状态，不自动找同名替代 |
| 旧混合目录中有开发者修改 | 保留内容与用户所有权，不直接执行覆盖迁移 |
| 脚本通过旧 API 读取其他路线 | 按固定兼容来源解析，不受仓库排序影响 |
| 资源变化后请求继续旧运行 | 有旧内容才恢复；仅有旧指纹时明确无法精确恢复 |
| 运行过程中触发仓库更新 | 正在使用的内容不会被更新流程改写 |
