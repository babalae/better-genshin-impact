# Pulonia：旧代码重构与迁移

[返回总览](../automation-system.md) · [用户故事](requirements.md) · [开发与验收计划](development-plan.md)

列出必须解耦的现有代码和一次性数据迁移策略。新菜单达到约定替代范围并通过用户验收后，才进入旧菜单切换。

## 原项目需要怎样重构

| 部分 | 处理方式 |
| --- | --- |
| `ScriptControlViewModel`、`OneDragonFlowViewModel`、旧配置组/一条龙模型 | 新页面和新模型替代，不继续叠加新需求 |
| `ScriptService.RunMulti`、`TaskRunner` | 新树引擎接管编排；过渡期仅用于未迁入口，最终不在新调用链里 |
| `ISoloTask` 和既有内置任务 | 初期适配成能力，逐项补强类型参数、结果和取消；不能包装 `TaskRunner` 后仍吞掉错误 |
| `ScriptProject` | 分离资源描述、参数编辑器、脚本执行器；保留引擎与脚本 API 兼容面 |
| JS `Dispatcher.RunTask`、`Genshin` 等 | 移除 ViewModel 取配置，转向能力注册表和本次上下文；旧名称提供兼容映射 |
| `TaskContext`、`RunnerContext`、`CancellationContext` | 新代码使用运行作用域上下文；旧任务在串行隔离适配层中渐进迁移，不能假定 AsyncLocal 已解决全部静态共享状态 |
| `GameRuntimeService`、输入框架、截图 Provider | 复用；增加租约/所有权与取消衔接，保留已有线程要求 |
| `TaskTriggerDispatcher` | 保持截图帧实时辅助职责；与定时/热键请求触发器明确分离，支持动作作用域撤销 |
| 完成日志、锄地统计、断点记录 | 新账本与节点结果成为依据；旧日志可作历史展示，未经证实不得直接导入为某账号的可靠 CD |
| 全局 `AllConfig` 与各功能设置页 | 设备配置保留，业务参数变成类型设置与共享预设；取消页面之间隐式取值 |
| 仓库与路线/脚本管理 | 保留资源获取和文件格式适配能力，新任务库接管查找、添加、编辑入口 |
| 快捷键与启动命令 | 统一提交请求，取消直接调用页面执行方法的分支 |
| d-v3 的任务树模型与树表、选择器、记录详情 | 作为新实现参考，按 Pulonia 命名迁入；保留交互，补稳定 ID、参数校验、懒加载和保存边界 |
| d-v3 的 Converter / Factory / BaseGearTask 树 / Runner 链 | 合并重复转换与调度职责；允许一次构建只读执行树，保留有价值的强类型参数与行为绑定；旧文件迁移单独处理 |
| d-v3 的 EventBus / HistoryRecorder | UI 进度用轻量通知；关键结果直接等待文件保存，历史写入由 Store 完成 |
| d-v3 的 Quartz 配置与 Job | 不迁入；转换可表示的日程，其余规则明确列出迁移差异 |

不需要先重写识别、地图匹配、战斗和所有路线算法。真正的前置重构是：显式参数、真实结果、可取消生命周期、状态作用域、输入所有权。

### 旧数据如何处理

“放弃旧实现”可以同时保留一次性导入器：把旧配置组转换为 `group` 加具体类型节点，把一条龙转换成新计划，把旧功能设置提取为预设。d-v3 的 `GearTaskDefinitionData / GearTaskData` 按原有 `root_task / children` 直接迁移，补 ID，转换参数字符串和目录类型；不要求重新手工录入。导入器应识别重复名称、旧周期语义、反射方法和无法映射的参数，生成差异报告。

保留原始文件和注释，迁移只写新存储。旧版无法确认账号归属的成功记录只读展示或让用户显式归属，不默认影响新账号额度。新入口达到功能对等后移除旧菜单，最终执行只有一套引擎。
