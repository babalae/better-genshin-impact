# 步骤 6：CD、历史与节点续跑验收说明

[返回开发计划](../../development-plan.md) · [结果与存储设计](../../results-and-storage.md) · [执行与续跑设计](../../execution.md)

步骤 6 使用 `User/Pulonia/state.json` 统一保存当前队列、活动运行、未决操作和 CD/额度；结束结果写入 `User/Pulonia/history/<planId>/<runId>.json`。运行页会同时列出当前状态与跨重启历史。

## 1. 历史与节点续跑

1. 运行一个包含多个纯 C# 或 Shell 节点的计划，让中间节点失败或取消运行；重新启动 BetterGI，确认历史、节点结果、结构化完成程度和证据仍可查看。
2. 选中该历史并点击“继续上次”，确认沿用历史快照、跳过已经成功的节点，从第一个未完成节点继续。
3. 在节点结果列表选中任一节点，点击“从选中节点开始”，确认新运行显示关联的原运行 ID，并按原快照的节点顺序从该地址开始。
4. 修改原计划后再继续历史，确认续跑仍使用旧参数；修改或删除旧路线、JS、录制资源后继续，确认资源指纹不一致时明确拒绝精确续跑。

## 2. 日、周、月、滚动 CD 的受控样例

新增“进程内 C#”节点，在参数中把 `operation` 分别设为：

- `sample.ledger.daily`：账号作用域，每日 4 点重置，额度 1。
- `sample.ledger.weekly`：世界作用域，每周一 4 点重置，额度 1。
- `sample.ledger.monthly`：账号作用域，每月 1 日 4 点重置，额度 1。
- `sample.ledger.rolling`：世界作用域，确认后滚动冷却 60 秒。

可附加 `event_key`、`units`、`occurred_at`、`report_twice` 和 `delay_milliseconds`。第一次运行后，运行页“当前 CD 与额度”应显示作用域、确认时间、证据来源和下次可执行时间/周期；同一作用域再次运行会按规则跳过。`report_twice: true` 会连续提交相同事件，账本只能增加一次。

进程内调用可以分别填写 `AccountId`、`WorldOwnerAccountId`、`Server` 和 `ServerUtcOffsetMinutes`。用两个已绑定账号提交相同日/月样例应各自计数；两个账号填写同一世界拥有者运行周/滚动样例应共享限制。计划名、节点 ID 和计划复制不参与 CD 身份。

## 3. 部分成功与崩溃窗口

1. 将 `operation` 设为 `sample.ledger.partial`。样例会先同步保存确认事件，再返回“部分成功”；确认计划失败但该局部事实仍保留，重新运行不会重复消费。
2. 将任一账本样例的 `delay_milliseconds` 设为较大值。节点进入运行后直接结束 BetterGI 进程，再启动；确认遗留活动运行变成“待处理”，未决操作阻止“继续上次”自动重放。
3. 核验游戏/样例状态后，在历史中选定节点并点击“从选中节点开始”。界面必须再次确认；确认后才释放该未决占用并建立关联运行。

## 4. 文件一致性与恢复

1. 正常结束运行后确认历史文件已写入，且 `state.json` 中不再保留对应 `pending_archives`；归档期间中断后重启，应按同一 `runId` 幂等补写，不能再次执行任务。
2. 人为破坏 `state.json`、保留有效 `state.json.bak` 后启动，确认界面提示发生备份回退，并要求核验遗留操作。
3. 同时破坏正式状态和备份，或制造状态写入失败，确认服务停止新增自动运行，不把账本重置为空继续执行。

旧 JS、路线和录制回放目前只会报告“执行结束但未核验”，不会仅凭正常返回写入游戏资源 CD。真实拾取、奖励、消耗等高精度完成事件仍需相应能力在后续识别覆盖中逐项接入。
