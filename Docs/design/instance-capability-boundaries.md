# 三种实例的能力边界与 IPC 规划

状态：边界确认、现状核对与规划，2026-10-26，基于 `refactor/20260930` 分支代码。2026-10-31 按[实例、账户与路线 CD 统筹设计](instance-account-model.md)更新，相关代码已于 2026-11-01 实施，待用户验收，见[统筹设计第 15 节](instance-account-model.md#15-实施记录)。

相关文档：术语见 [CONTEXT.md](../../CONTEXT.md)「多实例协作」；实例、账户、运行与进度的归属见[实例、账户与路线 CD 统筹设计](instance-account-model.md)；协议细节见[多实例命名管道协议](multi-instance-ipc.md)；配置落盘见[配置持久化链路](config-persistence.md)；Pulonia 定时见[触发与热键](pulonia/scheduling.md)、一步下发见[执行](pulonia/execution.md#跨实例执行一步下发)和[统筹设计 6.3](instance-account-model.md#63-一步下发)；运行环境见 [GameRuntime 设计](game-runtime.md)。

本文回答两个问题：每种实例能做什么、不做什么；实例之间的 IPC 管道负责什么、不负责什么。各节先给规则，再列现状差距。Pulonia 运行、账户和触发器相关的规则按统筹设计书写，代码已于 2026-11-01 实施，各节的现状差距只保留与统筹设计无关的条目；其他标“规划”的条目尚未实现。

已确认的总边界：

1. 所有实例都启动完整的 BetterGI 主界面，并可从本实例界面直接发起在本实例执行的任务，包括 Pulonia 计划。
2. 只有主实例能通过多实例 IPC 枚举、唤起、关闭、下发任务或停止其他实例。子实例不能控制或访问其他实例。

## 1. 三种实例

| 实例 | 代码中的类型 | 定位 | 如何启动 | 数量 |
| --- | --- | --- | --- | --- |
| 主实例 | `Primary`（根实例） | 本机执行实例，也是唯一的实例管理入口 | 不带 `--instance` 启动，抢到根管道即为主实例 | 每个 Windows 用户 1 个 |
| 桌面分身 | `ChildSession` | 在另一个 Windows 会话里运行本地原神，可从完整主界面执行本实例任务 | 主实例首页「桌面分身」建立 RDP 会话，登录完成后用临时计划任务以 `--instance childSession` 拉起 | 每个会话 1 个；目前每个 Windows 用户同时只有 1 个 |
| 云原神网页版实例 | `WebView` | 以一个具名云原神网页环境为执行对象，可从完整主界面执行本实例任务 | 主实例首页「云原神网页版」卡片，以 `--instance webview --instance-name <名> start` 拉起 | 每个实例名 1 个，可同时运行多个 |

后文把桌面分身和云原神网页版实例统称为子实例，云原神网页版实例简称云原神实例。

```text
主实例 primary（完整主界面；自己的 Pulonia 队列；唯一的实例管理入口）
 ├─ 桌面分身              完整主界面；自己的 Pulonia 队列；执行实例 child_session
 ├─ 云原神 · 小号A        完整主界面；自己的 Pulonia 队列；执行实例 webview:小号a
 └─ 云原神 · 小号B        完整主界面；自己的 Pulonia 队列；执行实例 webview:小号b
```

所有子实例只连接主实例，子实例之间不通信。该连接只允许主实例发起跨实例控制；子实例本地执行任务不经过 IPC。

实例键是执行实例的稳定标识，重启后不变：`primary`、`child_session`、`webview:<小写实例名>`。对应的实例目录是 `User/Pulonia/instances/` 下的 `primary`、`child_session`、`webview-<小写实例名>`，见[统筹设计 6.1](instance-account-model.md#61-实例键)。桌面分身的实例键不带会话号，前提是每个 Windows 用户同时只有一个桌面分身；会话号在分身重建后可能变化，只用于运行时寻址（统筹设计 A1，已决定）。

## 2. 基本原则

1. **本地执行自治。** 每个实例都有完整主界面和完整的 Pulonia 协调器，可直接决定“本实例做什么”并在自己的游戏环境中执行。本地发起、本地停止和本地状态展示都不经过多实例 IPC。
2. **跨实例控制集中。** 只有主实例能管理实例，或决定“让其他实例做什么”：枚举、唤起、关闭、下发任务、远程停止，都由主实例负责。主实例只检查自己负责的定时，并独占计划热键；子实例自己检查自己负责的定时。子实例不能把任务下发给主实例或其他子实例，也不能查询、唤起或控制其他实例。在任一实例的界面编辑共享计划（包括触发器的执行实例）不算跨实例控制：到点运行仍由执行实例自己检查和决定。
3. **主实例也是执行实例。** 主实例不是纯控制面板。未指定执行实例时，任务就在主实例执行；子实例界面发起的任务则固定在本实例执行。
4. **一个实例对应一个游戏环境。** 同一实例同一时刻只有一个自动化任务占用游戏（进程内的 `TaskControl.TaskSemaphore`），不同实例之间并行。同一账户同一时刻只能被一个运行占用，不论在哪个实例。
5. **共享配置，弱一致。** 所有实例共用程序目录下的 `User/`。各进程启动时把配置读入内存，修改后整份写回，后写者覆盖。不做跨实例实时同步，也不加跨实例锁。
6. **运行归执行它的实例，进度归账户。** 每个实例都有自己的 Pulonia 队列和运行状态 `User/Pulonia/instances/<目录名>/state.json`，只由本实例写入。主实例一步下发的运行也由执行它的子实例协调、执行和记录；主实例只显示子实例回报的状态，不另存一份。账户进度（完成记录、首领领奖次数）按账户存放在 `User/Pulonia/accounts/<账户 ID>/`，由执行运行的实例写入。运行历史写入所有实例共用的 `User/Pulonia/history/`，每个实例只写自己的运行。具体见第 5 节。
7. **实例差异写在代码里，不写进共享配置。** 例如云原神实例固定用 WGC 截图，桌面分身固定以 1920×1080 窗口化启动原神，都按实例类型在代码中决定，不修改共享配置。
8. **IPC 只传主实例的一步下发和必要状态。** 主实例经 IPC 管理子实例、下发独立任务和手动“运行于”的 Pulonia 运行；子实例只回报这些由主实例下发的任务状态。配置、日志、截图、Pulonia 定时触发和计划热键不经过 IPC。账户目录、实例当前账户、账户占用、在线标记和账户进度通过 `User/Pulonia` 下的共享文件读写，也不经过 IPC。子实例自己的任务不通过 IPC 提交。

## 4. 执行

### 4.1 任务从哪来、在哪跑

| 任务来源 | 发起方 | 执行位置 | 是否经过 IPC |
| --- | --- | --- | --- |
| 实时触发器 | 各实例自己 | 本实例 | 否 |
| 独立任务 | 任一实例都可从自己的界面发起；只有主实例可选择其他在线实例 | 本实例，或主实例选中的实例 | 仅主实例远程下发时用 `task.*` |
| Pulonia 计划，手动运行 | 任一实例都可从自己的界面发起；只有主实例可在“运行于”中选择其他在线实例，可多选 | 子实例发起时固定本实例；主实例发起时为选中的各实例，每个实例各一次运行 | 仅主实例向子实例下发时用 `pulonia.run.*` |
| Pulonia 计划，定时 | 触发器的各执行实例自己检查；执行实例为空时由主实例检查 | 本实例；一个触发器选了多个执行实例时，各实例各执行一次 | 否 |
| Pulonia 计划，计划快捷键 | 主实例注册 | 主实例 | 否 |
| Pulonia 计划，`--pulonia-run` | 启动参数所在实例 | 本实例 | 否 |
| 旧一条龙、调度器脚本组 | 本实例界面或命令行 | 本实例 | 否 |

### 4.2 规则

- 子实例从自己的界面发起任务时，执行实例始终是本实例，不查询在线实例，也不经过 IPC。界面不提供“运行于”选择器或任何远程停止入口。
- 跨实例执行只能由主实例发起，并且只走两条路：独立任务（单个任务）和 Pulonia（计划）。旧一条龙和调度器保持本地执行，不扩展跨实例控制。需要由主实例安排子实例批量执行时，用 Pulonia 并选择执行实例。
- 跨实例下发的任务使用主实例给出的参数。独立任务参数由主实例构造后随 `task.start` 下发，子实例不按自己的内存配置重新拼参数。Pulonia 运行只下发计划 ID、计划修订号和执行范围；子实例读取共享的计划，修订号一致才生成快照，不一致时拒绝，提示“计划已变更，请重新运行”。运行账户由子实例在运行开始时按自己的当前账户确定。
- 同一实例内，不同来源的任务竞争同一把任务锁。独立任务、旧一条龙、调度器拿不到锁时直接拒绝；需要游戏的 Pulonia 节点会等待锁释放。
- 每个实例有自己的 Pulonia 队列。本地提交和主实例下发的运行都进入执行实例自己的队列，不再共用主实例队列。同一实例串行，不同实例之间并行。同一账户不能在两个实例同时运行：运行开始时取得账户占用（`User/Pulonia/accounts/<账户 ID>/run.lock`），取得失败时运行进入待处理，不排队等待，见[统筹设计 4.5](instance-account-model.md#45-账户占用)。
- 停止运行：每个实例只能停止本实例的运行；主实例还可以用 `pulonia.run.cancel` 停止自己下发的运行。
- 断线处理：
  - 主实例崩溃或 IPC 断开时，不取消子实例已接受的运行，子实例照常执行和记录。断开期间主实例页面把这些运行显示为“连接断开，状态未知”，不能远程停止，需要在子实例界面停止。主实例的正常退出仍按第 6.1 节的退出保护处理（统筹设计 A2）。
  - 子实例重新连上主实例后，补发一次主实例所下发、尚未结束的运行状态。
  - “运行于”只列出在线的子实例。
  - 子实例自己发起的运行不依赖 IPC，主实例是否在线都照常执行。
  - 定时触发不依赖主实例在线。每个执行实例自己检查定时、在本地提交，主实例崩溃或断开不影响子实例的定时，见 7.2。

### 4.3 现状差距

- 主实例看不到子实例本地发起的独立任务、旧一条龙或调度器，此时下发的独立任务可能被子实例任务锁拒绝。统筹设计只让执行记录页显示各实例的 Pulonia 运行，其余本地任务仍不可见，见 9.5。

## 5. 配置

### 5.1 数据分类

| 数据 | 位置 | 谁会写 | 并发行为 |
| --- | --- | --- | --- |
| 应用配置（含 `ChildSessionConfig`） | `User/config.json` | 所有实例 | 500 ms 防抖后整份写回，后写者覆盖；没有热重载 |
| 脚本组、旧一条龙配置、路线、脚本等用户数据 | `User/ScriptGroup`、`User/OneDragon`、`User/AutoPathing` 等 | 任意实例 | 按文件原子替换，后写者覆盖 |
| Pulonia 计划、设置方案、计划顺序、账户目录 | `User/Pulonia/plans`、`profiles`、`accounts.json` 等 | 所有实例 | 修订号检查加跨进程写锁 `.writer.lock`，冲突时报错，不静默覆盖 |
| 实例设置（实例当前账户） | `User/Pulonia/instances/<目录名>/settings.json` | 该实例；主实例也可修改子实例的设置 | 原子替换，后写者覆盖 |
| 账户进度（完成记录、首领领奖次数） | `User/Pulonia/accounts/<账户 ID>/route-completions.json`、`boss-rewards.json` | 任意实例，按运行账户写入；任一实例的界面都可以清除完成记录 | `.writer.lock` 内读改写，不丢更新；其他实例按文件修改时间发现变化 |
| 账户占用、在线标记 | `User/Pulonia/accounts/<账户 ID>/run.lock`、`User/Pulonia/instances/<目录名>/online.lock` | 运行中的运行、运行中的实例 | 运行或实例存续期间以“允许他人读、不允许他人写”的方式打开，进程退出由系统释放 |
| 实例运行状态（排队请求、活动运行、待归档运行，以及本实例负责的定时触发器的游标） | `User/Pulonia/instances/<目录名>/state.json` | 该实例 | 单写者；不包含账户进度 |
| Pulonia 运行历史 | `User/Pulonia/history/<planId>/<runId>.json`，所有实例共用 | 执行该运行的实例 | 按运行 ID 幂等写入，每个实例只写自己的运行 |
| 狛荷屋记录 | `User/AccountRecords/<uid>/`，UID 列表来自账户目录 | 任意实例 | 狛荷屋自己的跨进程互斥 |
| 云原神登录态等网页数据 | `WebView2Data/CloudGame/<实例名>` | 对应的云原神实例；主实例负责新建和删除 | 按实例名隔离 |

实例目录名：主实例为 `primary`，桌面分身为 `child_session`，云原神实例为 `webview-<小写实例名>`。完整布局见[统筹设计第 8 节](instance-account-model.md#8-存储布局)。

`ChildSessionConfig` 虽然叫桌面分身配置，实际是主实例上 RDP 窗口的设置（窗口位置、置顶、游戏鼠标模式、静音、观看模式等），由主实例读写，不是分身进程自己的配置。

### 5.2 “不严格一致”的具体含义

保证：

- 配置文件不会写坏：先写临时文件再原子替换，临时文件名带进程号，实例之间不会踩到同一个临时文件。
- 跨实例下发的独立任务使用发起方的参数；Pulonia 运行用计划修订号保证子实例执行的是主实例提交时的计划（见 4.2）。
- 启动子实例前，主实例先把未保存的配置写盘（桌面分身和云原神实例的启动器都会 `Flush`），子实例启动时读到的是主实例当时的配置。
- 独立任务启动时重新读取磁盘上的配置，任务内部用到的其他配置项取最新落盘值。

不保证：

- 一个实例修改配置后，其他正在运行的实例立即看到。实时触发器等常驻功能使用各自启动时读到的配置。
- 两个实例分别修改不同字段时都能保留。写回是整份覆盖，后写者会用自己内存里的旧值覆盖对方改过的字段。

使用约定：

- 以主实例作为配置的编辑入口。改完后需要子实例生效时，重启子实例。
- 子实例主界面允许修改配置，但不要同时在多个实例里修改共享配置。

### 5.3 规划规则

- 子实例只在用户于本实例界面显式修改时写通用配置 `config.json`，启动和运行过程中不主动写。Pulonia 数据不受这条限制：子实例运行时会写本实例运行状态、运行历史和账户进度，所以 `.writer.lock` 和修订号保留（原 Pulonia 待定项 D15 的结论）。
- 按实例区分的行为由实例类型在代码中决定，不新增“每个实例各填一份”的共享配置项。唯一的例外是实例当前账户：它描述“这个游戏环境登录着谁”，不描述“怎么跑”，按实例保存在 `instances/<目录名>/settings.json`。通用配置不按实例或账户拆分。
- 需要按账户区分的设置，用不同的计划或设置方案表达，不做账户养成配置，见[统筹设计第 7 节](instance-account-model.md#7-配置)。
- 不引入配置热重载，也不经 IPC 同步配置。某项配置确实需要子实例与主实例一致时，优先改为随任务请求下发。
- Pulonia 计划和账户目录已有修订号保护，允许在所有实例中编辑。
- Pulonia 的计划定义和账户目录继续共享。运行状态按执行实例隔离：不论本地提交还是主实例下发，运行都写执行实例自己的 `state.json`；历史写共享目录，每个实例只写自己的运行，主实例不为下发的运行另存记录。账户进度按账户存放，先写完成记录、再写节点结果，见[统筹设计 5.4](instance-account-model.md#54-写入顺序)。

### 5.4 现状差距

- 所有实例启动时都会无条件保存一次配置（`App.xaml.cs` 中推理配置规范化后、界面语言迁移时）。子实例刚读入配置，覆盖风险很小，但不符合 5.3 第一条。
- 子实例运行中由任务自动改动的配置（运行状态混在配置里的字段，见[配置持久化链路](config-persistence.md)第 3 节）同样会整份写回。

## 6. 界面

### 6.1 各实例的界面

主实例：

- 主窗口全部页面和托盘。
- 实例管理：首页「桌面分身」「云原神网页版」卡片；标题栏在线子实例列表，可打开或关闭子实例，每项还显示子实例的当前账户和正在运行的计划名，当前账户可以在这里修改；桌面分身 RDP 窗口。
- 跨实例操作入口：有子实例在线时，独立任务按钮弹出多实例窗口；任务计划页和新一条龙页显示“运行于”，可多选，每项显示实例名和当前账户，如“云原神 · 小号A — 乙”，账户可以就地修改。
- 退出保护：还有云原神实例在线，或桌面分身会话仍存在时，关闭主窗口和托盘退出都会被拦下，提示先关闭子实例。

桌面分身：

- 在分身桌面里运行完整主窗口，用户通过主实例的桌面分身窗口查看和操作。标题栏显示“桌面分身”徽标。
- 可从完整导航页面发起本实例任务。隐藏实例管理和跨实例控制入口；独立任务、新一条龙等执行实例固定为本实例，不显示其他实例选择器。
- 启动时只应用主题，不执行检查更新、版本迁移、推理验证、OCR 预热等维护步骤。

云原神实例：

- 显示完整 BetterGI 主窗口，标题栏显示“云原神 · {实例名}”徽标；首页通过预览进入客户区固定为 1920×1080 物理像素的云原神宿主窗口。
- 可从完整导航页面发起本实例任务。隐藏实例管理和跨实例控制入口；执行实例固定为本实例，不显示其他实例选择器。
- 当前不提供托盘；关闭云原神宿主窗口会退出该实例，遮罩窗口照常显示。

所有实例：账户目录有多个账户时，标题栏显示账户徽标“账户：乙 ▾”，点击可以改为其他账户或“管理账户”；只有一个账户时不显示。Pulonia 分组都显示任务计划、新一条龙、执行记录和账户四个页面，见[统筹设计第 9 节](instance-account-model.md#9-界面)。

### 6.2 规划规则

- 所有实例保留完整页面，用于配置、查看状态以及直接执行本实例任务。只有主实例显示实例管理和跨实例控制；子实例页面不得通过 IPC 查询或操作其他实例。
- 影响程序目录或所有实例的维护操作只放在主实例，例如检查更新、脚本订阅更新和版本迁移。共享配置允许在子实例编辑，但遵守第 5 节的弱一致约束。
- 同一个子实例在标题栏、独立任务窗口、“运行于”中使用一致的名称和图标。
- 每个实例都能修改本实例当前账户（标题栏账户徽标、账户页顶部）。修改子实例当前账户的入口只在主实例：标题栏实例列表和“运行于”。修改直接写共享的实例设置文件，不经过 IPC。
- “运行于”中，指定账户的计划只能选一个实例，默认选中当前账户就是该账户的实例；跟随当前账户的计划可以选多个实例。提交前检查选中实例的当前账户是否重复，或与正在运行的账户重复，并在提示中直接修改。实际做法：提示只说明问题，用户选“否”后展开“运行于”，在那里修改各实例的当前账户（[统筹设计第 15 节](instance-account-model.md#15-实施记录)）。
- 执行记录页在每个实例都显示全部实例的 Pulonia 运行：已结束的从共享历史目录读取，排队和运行中的读各实例的 `state.json`。

### 6.3 现状差距

- 桌面分身的托盘仍有“检查更新”，而 `UpdateService` 不判断实例类型，可能在主实例运行时更新同一个程序目录。
- 桌面分身没有 OCR 预热（`MainWindowViewModel.OnLoaded` 对非主实例提前返回），首次识别会慢一些。云原神实例在 `ApplicationHostService` 中做了预热，两者不一致。
- 名称和图标不一致：标题栏用 Globe 图标和“云原神 · 名 / 桌面分身（Session N）”，独立任务窗口用 Cloud 图标和“云原神（名）/ 桌面分身（会话 N）”。
- `ChildSessionService` 在子实例中也会构造，并启动 500 ms 轮询，子实例用不到。
- 子实例页面中仍有“请在主实例运行”或只支持命令行触发的入口，需要逐项改为本实例直接执行；只有跨实例选择和控制继续限制在主实例。

## 7. Pulonia 定时触发

### 7.1 现状

- 所有实例都可以编辑并保存计划。计划变化版本号只在本进程内递增，所以其他实例最多 30 秒后才读到。

### 7.2 规划

按[统筹设计 6.4](instance-account-model.md#64-触发器)，已于 2026-11-01 实施：

1. **每个执行实例自己检查定时，共享计划不会重复触发。** 主实例、桌面分身和云原神实例都运行 `PuloniaTaskTriggerHost`，每秒检查一次，只处理执行实例包含本实例实例键的定时触发器；执行实例为空的触发器只由主实例处理。一个（触发器，执行实例）组合只有一个检查者：主实例只有一个，桌面分身同时只有一个，同名云原神实例由实例名互斥体保证只运行一个。计划快捷键不属于定时，只在主实例注册和执行，见 8.2。
2. **定时触发器指定执行实例，可多选。** 触发器的 `instances` 字段是执行实例键的列表，为空时只在主实例执行，只对定时触发器有效。计划指定了账户时只能选一个执行实例，因为同一账户不能同时运行。选了多个执行实例时，保存前检查这些实例的当前账户是否重复。触发器不再有 `account_id`。
3. **到点时由执行实例在本地提交。** 运行进入本实例的队列，不经过 IPC。主实例不替子实例检查定时，也不替它下发。一个触发器选了多个执行实例时，每个实例各自检查、各自提交一次，各实例并行运行。
4. **游标按（计划、触发器）记录在执行实例自己的 `state.json` 中**，入队与游标前移在同一次替换中提交。一个触发器选了多个执行实例时，每个实例各有一份游标，各自前移，互不影响。实例重启后按游标继续，不会重放已处理的时刻。
   - 执行实例没有运行：没有进程检查它的定时。实例启动后按自己的游标和补触发规则（`catch_up`、`window_minutes`）处理遗漏，仍在允许延迟时间内的最近一次补跑，超过的记为遗漏。不改到其他实例执行，主实例也不替它启动实例。
   - 执行实例已被删除（例如删掉了云原神实例）：没有实例检查这个组合，触发设置页提示“执行实例不存在”。
   - 触发状态只在执行实例的内存中。其他实例的触发设置页每 10 秒读取一次它的 `state.json` 游标和 `online.lock`，显示上次触发时间和是否在线，不经过 IPC。
5. **忙碌策略在执行实例的队列上判断。** “忙碌”指该实例里同一计划已有未结束的请求。同一时刻多个触发器到点时，执行实例不同就各自提交、并行运行；执行实例相同就依次进入该实例的队列，忙碌时按各触发器的忙碌策略处理。
6. **子实例接受本地 Pulonia 提交。** 子实例从界面、自己的定时触发器或 `--pulonia-run` 提交时，执行实例固定为本实例，由本实例队列协调，不经过 IPC，也不转发给主实例。任何指向其他实例的请求都拒绝，并提示跨实例运行只能从主实例发起。
7. **计划变更的感知延迟维持现状。** 本实例保存计划后下一轮重读，其他情况每 30 秒比较计划文件修改标记。在另一个实例修改触发器，执行实例最多 30 秒后按新设置检查，属于弱一致范围。需要更快时缩短周期或监听计划目录，不经 IPC。

以上按[统筹设计第 13 节](instance-account-model.md#13-实施顺序)的顺序实施：先移出账户进度（第 2 步），再拆分实例运行状态（第 4 步），之后是一步下发（第 5 步）、账户占用（第 6 步）和触发器的执行实例（第 7 步）。

## 8. 快捷键

### 8.1 现状

| 快捷键 | 主实例 | 桌面分身 | 云原神实例 |
| --- | --- | --- | --- |
| 应用快捷键，全局注册 | 注册在主会话 | 注册在分身会话 | 不注册 |
| 应用快捷键，键鼠监听 | 截图器运行时生效 | 截图器运行时生效，作用于分身会话 | 不注册 |
| Pulonia 计划快捷键 | 注册 | 不注册 | 不注册 |
| 跨实例转发 | 无 | 无 | 无 |

- 应用快捷键在创建首页时注册（`HomePage` 注入 `HotKeyPageViewModel`），所以主实例和桌面分身都会注册一整套，键位来自共享的 `HotKeyConfig`。
- 云原神实例与主实例在同一会话。全局热键只能被一个进程注册，键鼠监听也会和主实例重复响应，所以云原神实例不注册任何快捷键。
- 全局热键和键鼠钩子只作用于所在会话。桌面分身的快捷键只在分身会话收到键盘输入时触发，也就是用户在主实例的桌面分身窗口里操作时。（按 Win32 行为推断，未实测）

### 8.2 规则

- 快捷键只控制所在会话里的那个实例，不做跨实例转发。
- Pulonia 计划快捷键只在主实例注册，按下后只在主实例执行，不转发给子实例，也没有执行实例选项。子实例不注册计划快捷键，原因见 8.1：云原神实例与主实例在同一会话，全局热键只能被一个进程注册，键鼠监听会重复响应；桌面分身只在焦点位于分身窗口时收到输入。需要在子实例运行计划时，用子实例自己的界面、定时触发器，或主实例的“运行于”，见[统筹设计 6.4.3](instance-account-model.md#643-计划热键)。
- 用户可以在子实例自己的主界面发起或停止本地任务。要从另一个实例远程控制子实例，只能使用主实例界面中的独立任务多实例窗口或 Pulonia 执行记录页；子实例界面不提供远程控制。
- 待验证：桌面分身窗口获得焦点、且开启“系统快捷键发送到远端”时，主实例的全局热键和分身里的同名热键哪个先响应。
- 可选规划：需要“一键停止全部实例的任务”时，在主实例增加一个快捷键，由主实例经 IPC 逐个发送 `task.stop` 和 `pulonia.run.cancel`。`pulonia.run.cancel` 只能停止主实例下发的运行。不做通用的快捷键转发。

## 9. IPC 能力范围

### 9.1 边界

所有子实例只连接主实例的根管道 `BetterGI.v2.user-<用户SID>.root`，只有同一 Windows 用户的本机进程能连接。管道拓扑不等于控制权限：只有主实例能主动访问和控制其他实例，子实例连接管道只是为了登记、接受命令并回报必要状态。

IPC 负责：

- 实例登记与发现：子实例连接后登记。主实例从管道句柄取得真实进程号和会话号，不信任子实例自报的身份。
- 生命周期：主实例唤起子实例窗口、请求子实例退出、转发重复启动的参数。
- 任务控制与状态回传：主实例发起独立任务启停、Pulonia 运行的一步下发与取消；子实例回报这些由主实例下发的任务状态，重连后补发尚未结束的 Pulonia 运行状态。
- 输入转发：主实例把用户的真实鼠标位移转发给桌面分身（游戏鼠标模式）。
- 预留：主实例访问云原神实例的自定义消息通道。

IPC 不负责：

- 配置同步或配置变更通知。
- 账户目录、实例当前账户、账户占用、在线标记和账户进度。这些都通过 `User/Pulonia` 下的共享文件读写。
- Pulonia 运行的快照、节点结果和历史。执行实例自己落盘，主实例不经 IPC 代写。
- Pulonia 定时触发和计划快捷键。定时由执行实例自己检查、在本地提交，计划快捷键只在主实例执行。
- 日志汇聚。各实例只写共享日志文件（带实例标识），外部访问的日志 WebSocket 只能看到主实例的日志。
- 截图、文件等数据传输。
- 快捷键转发。
- 心跳。
- 远程重启子实例。子实例自行重启，主实例按 `--restart-from-pid` 接受新进程替换旧登记。
- 子实例之间通信，子实例向主实例提交任务，以及子实例经主实例中转访问其他子实例。

### 9.2 方向规则

- 业务请求只能由主实例发给子实例，子实例收到后校验来源必须是主实例。子实例不能调用枚举、查询、唤起、关闭、任务启停或消息转发等面向其他实例的操作。
- 子实例发给主实例的只有：连接登记、主实例所下发任务和 Pulonia 运行的状态回报，以及相对鼠标订阅等协议建立所必需的消息。这些消息不授予子实例控制权。
- 新增操作必须先归入上面两类之一。不属于“主实例控制子实例”或“子实例回报主实例已下发操作”的需求，不放进 IPC。子实例自己的本地任务既不提交，也不回报给主实例。

### 9.3 操作清单

| 类别 | 操作 | 方向 | 使用情况 |
| --- | --- | --- | --- |
| 登记 | `connection.open` | 子 → 主 | 使用中 |
| 生命周期 | `activation.dispatch` | 主 → 子 | 使用中：标题栏“打开实例”、转发重复启动参数 |
| | `application.shutdown` | 主 → 子 | 使用中：标题栏“关闭实例” |
| 独立任务 | `task.start`、`task.stop`、`task.status.get` | 主 → 子 | 使用中 |
| | `task.status.changed` | 子 → 主 | 使用中；开放子实例本地任务后仍只回报主实例下发的运行 |
| Pulonia | `pulonia.run.submit`、`pulonia.run.cancel` | 主 → 子 | 使用中，已取代 `pulonia.node.start`、`pulonia.node.cancel`；任务计划页和新一条龙页的“运行于”选子实例时发送 |
| | `pulonia.run.changed` | 子 → 主 | 使用中，已取代 `pulonia.node.finished`；只回报主实例下发的运行，重连后补发尚未结束的运行（`pulonia.node.report` 已随通用额度框架删除） |
| 输入 | `input.relativeMouse.subscribe` | 桌面分身 → 主 | 使用中，连接后自动订阅 |
| | 相对鼠标二进制批次与回执 | 批次主 → 桌面分身，回执反向 | 使用中 |
| | `input.relativeMouse.unsubscribe` | 桌面分身 → 主 | 只有处理方，没有发送方 |
| | `input.relativeMouse.state` | — | 只定义了名称 |
| 云原神消息 | `webview.list`、`webview.send`、`webview.message` | 主 → 云原神实例；消息回报反向 | 基础设施已有，没有业务调用方；拒绝桌面分身经主实例中转 |
| 诊断 | `ping` | 主 → 子 | 只有处理方，没有发送方；子实例不主动探测其他实例 |

### 9.4 开发约束

- 全部是请求-响应，没有单向通知。请求统一超时 5 秒。
- 同一连接上收到的请求逐个处理。处理器里不要做耗时操作，也不要在同一连接上反向发请求并等待，否则会一直阻塞到超时。长任务一律“立即确认，之后回报状态”，与 `task.start`、`pulonia.run.submit` 一致。
- 根管道的服务端必须按连接角色校验操作方向。来自子实例的业务控制请求即使协议中存在同名处理器，也必须拒绝，不能把主实例当作子实例之间的代理。
- 单帧不超过 1 MiB。`pulonia.run.submit` 只传计划 ID、修订号等字段，原来约 900 KB 的派发负载上限已不再需要。
- 主实例和子实例必须是同一版本：信封版本号严格相等，枚举按整数序列化，不做兼容。
- 没有心跳。对端卡住但管道没断时，只能靠请求超时发现。

### 9.5 规划

- Pulonia 一步下发（已于 2026-11-01 实施）：新增 `pulonia.run.submit`、`pulonia.run.cancel`、`pulonia.run.changed`，删除 `pulonia.node.start`、`pulonia.node.cancel`、`pulonia.node.finished`，以及 `PuloniaRemoteExecutionBroker` 和 `PuloniaRemoteNodeHost`，见[统筹设计 6.3](instance-account-model.md#63-一步下发)。`pulonia.run.submit` 只用于主实例界面的手动“运行于”；触发器不经过 IPC，不为它新增操作。“运行于”多选和跨实例执行记录也已实施。
- 可选：主实例在下发前查询子实例的本地占用摘要，让主实例知道目标是否正被本地任务占用。该查询只能由主实例发起，不把子实例本地任务注册到主实例协调器。
- 可选：日志汇聚。子实例把日志批量回报给主实例，由外部访问的日志 WebSocket 统一输出。只在确实需要远程查看子实例日志时做。
- 可选：心跳。出现“子实例卡死但不断线”的实际问题后再加，可直接定时发送已有的 `ping`。
- 清理：`input.relativeMouse.state`、`input.relativeMouse.unsubscribe`、`ping` 和 `webview.*` 目前没有业务调用方。保留时必须收窄为主实例发起；否则在下次协议升级时删除。
- 明确不做：配置同步、快捷键转发、子实例之间直连或经主实例中转、子实例向主实例提交任务、子实例查询或控制其他实例。
